# ADR 0012：通过 pi-ai + OpenAI 兼容扩展实现通用供应商/模型覆盖

> **翻译说明：** 本页是与 [英文源决策](/adr/0012-universal-provider-model-coverage) 一一对应的机器辅助翻译。代码、协议字段和标识符保持原文；如翻译与英文源事实有歧义，以英文版本为准。

- 状态：已接受
- 日期：2026-07-25

## 上下文

产品需求：

> 供应商支持必须广泛覆盖市场厂商/模型，而不是一个小的固定集合。

自行实现并维护每个厂商 SDK 是不现实的。pi-ai 已提供多供应商抽象，且大多数长尾厂商都暴露 OpenAI 兼容 API。

## 决策

1. 使用 **pi-ai** 作为原生多供应商引擎
2. 将 **OpenAI 兼容供应商** 视为一等公民
3. 提供 **可刷新的模型目录** + **用户自定义模型 ID**
4. **不**强制实施会阻止未知模型的封闭产品允许列表
5. 在 UI 预设中暴露主要厂商，同时允许任意自定义端点

## 后果

### 正面
- 以可控的工程范围实现广泛的市场覆盖
- 为“支持市场厂商/模型”提供可行路径
- 在 pi-ai 有集成的场景提供原生质量
- 易于支持网关和本地模型服务器
- 为其他一切提供通用逃生通道
- 未来的厂商通常无需重写应用即可接入
- 目录无需重写应用即可持续演进

### 负面 / 权衡
- 能力质量因厂商而异
- 目录/能力元数据可能不完整（尤其是冷门模型），需要刷新/手动覆盖
- OpenAI 兼容的怪癖仍需要兼容性标志
- 目录新鲜度取决于刷新/捆绑快照

## 考虑的替代方案

1. **仅使用极小的固定厂商列表**（例如，仅 3-4 个顶级厂商）
   - 拒绝：无法满足全球化与用户预期
2. **自行构建并维护所有厂商 SDK**（例如，用 Rust 重新实现每个厂商 SDK）
   - 拒绝：与 pi-ai 重复，拖慢交付，维护成本高
3. **仅支持 OpenAI 兼容，不使用原生供应商**
   - 拒绝：对具有原生怪癖的主要厂商而言，UX/质量更差
4. **硬编码的封闭/固定模型允许列表**
   - 拒绝：模型每周都在变动；会阻碍高级用户
