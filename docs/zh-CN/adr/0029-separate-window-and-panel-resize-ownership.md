# ADR 0029：分离原生窗口与工作面板的尺寸调整归属

> ADR 0032 取代了在既有客户区内对面板进行响应式钳制、以及禁止一切由面板驱动的原生几何变更的条款。BrowserWindow 几何由主进程拥有、已提交的面板宽度由渲染器拥有、以及分隔条手势与提交规则仍然有效。

## 背景

此前，工作面板的可见性和分隔条提交会调用 `window/resizeBy`，以便 Electron 扩大或缩小原生窗口。渲染器的 `window.resize` 事件随后会推断用户是否移动了原生窗口右边缘，并将该变化量的一部分写回面板宽度。限时归属票据曾试图将这类程序化事件与真实的窗口手势区分开来。

这形成了一种循环式的归属模型：面板改变原生窗口，原生窗口又改变面板。它导致分隔条释放后出现第二次布局跳变、快速打开/关闭时产生过期的异步增长、在显示器边缘附近出现窗口位置漂移、产生平台相关的行为差异，以及在一次无关的原生窗口尺寸调整过程中偏好值被改动。

## 决策

原生窗口几何与渲染器列几何由各自独立的归属方拥有：

1. Electron 主进程独占拥有 `BrowserWindow` 的边界，并持久化实际的常规边界。支持的最小尺寸为 1040x700。
2. 渲染器在 localStorage 中拥有一个偏好的工作面板宽度。有效宽度由该偏好值针对当前视口、可见侧边栏和 MainChat 预留宽度进行钳制后得出。
3. 原生窗口边缘手势只调整外壳尺寸。它们可以临时钳制有效面板宽度，但绝不覆盖其偏好值。
4. 工作面板分隔条只调整内部列。指针运算以手势起始点为锚点；移动渲染按帧合并；释放时提交一次；Escape、指针取消和捕获丢失都会回滚。
5. 在任何平台上，打开、折叠、切换会话和关闭面板都不会改变原生边界。
6. 移除渲染器到主进程的 `window/resizeBy` IPC 方法、程序化尺寸调整归属票据、面板增长跟踪以及持久化宽度偏移量。

## 影响

- 分隔条反馈在释放过程中保持连续，而不再触发第二次原生尺寸调整。
- 原生边缘行为对称，并与平台窗口惯例一致。
- Windows、macOS 和 Linux 共用同一套面板交互模型。
- 临时受约束的面板在空间可用时会恢复到其偏好宽度。
- preload 接口面更小，Electron 的窗口状态持久化不再需要面板专用的偏移量。
- 常规边界独立于最大化/全屏状态读取，并在关闭时同步刷写，以免待处理的防抖导致其丢失。
- 打开面板会重新分配现有的客户区，因此在操作者调整分隔条或原生窗口之前，MainChat 可能变窄。

## 备选方案

### 保留 delta IPC 并添加请求标识符

已否决。请求标识符可以拒绝过期回复，但无法消除循环式的几何归属，也无法消除释放后的布局跳变。

### 让 Electron 拥有完整的三列布局

已否决。主进程并不知道渲染器的侧边栏状态或内容约束，而将分栏布局通过 IPC 迁移会引入延迟并造成 DOM 真相的重复。

### 为工作面板保留原生右边缘归属

已否决。边缘来源推断在无边框窗口、显示缩放、macOS 窗口装饰和 Wayland 下并不可靠。原生边缘应保留其标准含义：调整窗口大小。
