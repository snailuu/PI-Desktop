# ADR 0032：为停靠的工作面板预留原生宽度

## 上下文

ADR 0029 移除了工作面板变更与原生调整大小事件相互改写的循环所有权模型。它让面板成为现有客户端区域内的响应式列。这消除了竞态和释放后跳动，但打开面板仍会占用对话宽度，折叠面板又会让对话重新扩展，而原生窗口边缘调整大小可能会临时压缩面板。

预期的停靠行为更接近 Codex：面板拥有自己已提交的宽度；面板可见时，普通窗口会为其预留原生宽度；原生窗口边缘调整的是对话表面，而非工具表面。这需要受控的 BrowserWindow 几何，同时不恢复旧的基于增量的循环所有权。

## 决策

渲染器面板布局与 Electron 窗口几何保持为独立所有者，但它们通过幂等的目标状态预留进行协调：

1. 渲染器拥有一个已提交的首选面板宽度，范围包含 `364..720`。打开的停靠面板以该固定宽度渲染；视口、侧边栏和原生边缘变化都不会对其进行钳制或改写。
2. 预加载只暴露 `window/setWorkPanelReservation({ width: 0 | 364..720 })`。Electron 主进程返回 `{ requested, reserved }`，其中 `requested` 是规范化后的当前目标，`reserved` 是当前为其添加的原生宽度。重复使用同一目标不会产生累积效果。
3. 在普通窗口状态下，主进程根据持久化的基础边界加上目标预留推导出可见边界。它优先向右扩展，仅在必要时向左移动，以使结果保持在当前显示器工作区内。`reserved` 受可用工作区宽度上限约束。
4. 打开可见面板会请求其已提交宽度。折叠面板或关闭其最后一个资源会请求零，并对称地移除新增宽度以及任何由预留引起的 x 偏移。已提交的分隔条变更会将预留目标更新为新的已提交宽度。
5. 当工作区能够提供完整目标时，面板可见性和分隔条提交不会改变对话宽度。当工作区无法提供时，主进程会预留可用宽度，面板仍以其固定的已提交宽度渲染，对话则吸收不可避免的 `requested - reserved` 短缺量。
6. 当预留处于活动状态时，原生边缘调整大小只会改变基础窗口边界，从而只改变对话宽度。预留的原生宽度和渲染器的固定面板宽度保持不变。
7. 最大化和全屏窗口会记录最新的请求目标，但会推迟预留几何。返回普通状态时，会根据恢复的基础边界和当前显示器工作区，对该目标进行一次协调。
8. 将窗口移动到另一台显示器或改变显示器工作区几何时，会根据新的可用宽度协调同一目标。在同一个未变化工作区内的普通移动不会重新应用预留几何。
9. 持久化的普通边界是移除了活动预留宽度和预留引起的 x 偏移后的基础边界。因此重新启动时，绝不会将面板展开状态下的窗口外壳恢复为仅对话的窗口尺寸。
10. 只有当前可见的会话上下文可以设置预留。后台会话工件可以更新其保留的标签页，但绝不改变可见预留几何。

ADR 0029 中分隔条的锚定指针计算、帧合并预览、释放时提交以及取消回滚仍然有效。实时预览仍然是渲染器布局操作；只有成功提交才会改变原生目标。

## 后果

- 只要显示器工作区有足够的未使用宽度，打开和折叠面板都会保持对话宽度。
- 原生边缘手势只有一个可预测的效果：在面板保持固定的同时调整对话大小。
- 小显示器可能使对话宽度窄于其 360px 可读性目标，但绝不会静默压缩面板或破坏其已提交的首选项。
- 主进程拥有的是狭窄且列入允许列表的几何能力，而不是任意的增量调整大小通道。在快速的会话和资源转换期间，目标状态调用可以安全地重复。
- 窗口状态持久化以及最大化/全屏转换必须区分基础边界与临时预留几何。

## 备选方案

### 将所有列保留在当前客户端区域内

已拒绝，因为面板打开/折叠仍会继续调整对话大小，原生边缘手势也可能继续压缩面板。

### 恢复由渲染器提供的调整大小增量

已拒绝，因为增量不具备幂等性，并且会重新引入 ADR 0029 已移除的过期请求、双重调整大小和持久化歧义。

### 强制在显示器工作区之外预留完整空间

已拒绝，因为固定面板不得将原生窗口框架移出屏幕。预留可用宽度并仅将不可避免的短缺量分配给对话，可同时保持面板保真度和可操作的窗口框架。
