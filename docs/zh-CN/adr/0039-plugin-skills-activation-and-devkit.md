## 背景

`contributes.skills` 自 R1 起就是 manifest v1 的一部分：`validateManifest` 接受它，`examples/plugins/hello` 也附带了一个技能文件。但没有任何代码读取它。声明一个技能没有任何可观察的效果，因此这个贡献点只是文档，而不是功能。

创作路径在另一个方向上同样不完整。`.piplug` 包可以被安装，却无法被产出：host-core 拥有 `install_from_package`，而仓库中没有任何东西能够写出它所接受的仅含 store 的 zip。既没有模板，也没有安装前的 manifest 校验，而且对开发插件的每次源码修改都需要通过原生对话框重新选择其文件夹。

这两个缺口其实是同一个缺口：PI-Desktop 要求用户编写插件，却没有给他们这个闭环——脚手架、运行、检查、打包。

## 决策

1. **技能以受权限门控的目录形式到达模型，模型可从中加载。** `PluginRuntime` 在加载时为每个已声明的技能文件建立索引，仅针对被授予 `agent.prompt.inject` 的插件，且仅通过与受限 `fs` API 相同的包含性防护进行。系统提示词携带一个 `# Skills` 区段，每个技能一行——id、名称、适用性——模型按需通过 `Skill` 工具拉取正文，该工具由 Electron 主进程提供，因为插件目录位于那里。一个技能文档可以达到 128 KiB，一个插件可以教授 32 个这样的文档，因为未被读取的文档不产生任何开销（D174，该决策取代了本 ADR 最初的 16 KiB 整篇正文提示词注入做法）。
2. **提示词顺序是主机技能、然后插件技能、然后项目指令。** 越靠后的文本权重越高，因此用户自己的指令文件拥有最终话语权，已安装的插件可以细化内置指引，但反之不可。
3. **运行时复用以目录摘要为键，而非以正文为键。** 启用插件、撤销 `agent.prompt.inject` 或重命名技能都会改变模型读到的文本，因此会淘汰空闲运行时，而不是复用一个过期的提示词。对正文的编辑无需淘汰：`Skill` 工具在调用时读取该文件。
4. **插件创作作为第一方 devkit 交付，而不是作为插件。** `@pi-desktop/plugin-devkit` 负责脚手架、检查和打包；三个界面共享这一份实现——`pi-plugin` CLI、由 Electron 主进程提供的 `PluginScaffold` / `PluginCheck` / `PluginPack` 代理工具，以及插件页面上的模板操作。
5. **内置的插件开发技能仅对插件工作区激活**——即工作区根目录下存在 `manifest.json`，或其内部包含一个已加载的插件目录。普通会话只需为三份工具描述付出代价，其他什么也不用付出；脚手架会写入一个 manifest，从而在下一个提示词中激活完整技能。
6. **热重载不得扩大权限集。** 被监听的开发插件在保存时重载，但重载会先读取 manifest：若权限超出选择该文件夹时所批准的范围，重载将停止并报错，提示用户重新加载该插件。授权会随 manifest 向下收紧，因此被移除的权限将不再可用。

## 后果

- 技能文件现在是一种可执行表面。`agent.prompt.inject` 在权限矩阵中保持其高风险层级，并且是唯一的门控点；安装审查已经会显示它。
- `check` 通过意味着安装也会通过，因为 devkit 复现了 host-core 所执行的规则（仅含 store 的条目、2000 个文件、50 MB、无符号链接、无 `.git`/`node_modules`）。这些限制在 TypeScript 和 Rust 中重复实现，必须同步变更。
- 技能文件是在模型索取时才被读取，而不是每次提示词都读取，因此一次编辑会在下一次 `Skill` 调用时生效，而不需要任何技能的会话则什么都不读。目录元数据在加载时建立索引，因此重命名技能仍需重载——被监听的开发插件会在保存时完成这一点。
- 重载失败会让插件保持未加载但仍被监听，因此下一次保存即可恢复它。在这段时间窗口内，host-core 的注册表仍报告 `ready`：它没有用于运行时侧加载失败的 RPC，因此重载会通过一条 toast 和 `pluginChanged` 自行上报，正如插件崩溃时的做法一样。
- 技能 front-matter 解析位于插件 SDK（`parseSkillFrontmatter`）中，由运行时注册表、内置技能和 devkit 的 `check` 共享。

## 备选方案

### 将插件创作作为内置插件交付

已否决。插件无法产出 `.piplug`：`HOST_API_ALLOWLIST` 中没有归档 API，而添加一个就会把 zip 写入能力交给每个插件。脚手架还需要 `fs.write.workspace` 这一高风险权限，去实现本应由应用自身提供的能力。第一方意味着始终可用，没有权限提示，也没有先有鸡还是先有蛋的问题。

### 将插件开发技能注入每个会话

已否决。对永远不会编写插件的用户来说，在每个系统提示词中都放一份插件创作入门内容是纯粹的浪费。三份工具描述足以引导起步，而工作区门控会在它真正变得相关时恰好开启完整技能。

### 与技能共享 32 KiB 的指令链预算

已否决。技能来自第三方代码，而指令来自用户。共享预算会让已安装的插件挤占项目自身的规则。

### 无视 manifest，以先前授予的权限重载

已否决。授权集是针对特定 manifest 批准的。在 manifest 被编辑后复用它，会让一次文件写入在权限网关背后扩大能力——而权限网关正是插件系统存在所要守住的那条边界。
