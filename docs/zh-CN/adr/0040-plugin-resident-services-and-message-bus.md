## 上下文

路线图中有两项因同样缺失的能力而被阻塞。

**后台服务。** 插件只有在被调用时才能工作：某个命令、某个工具或 `onLoad`。一个 watcher、一个轮询器或一个同步 worker 没有受支持的去处。没有什么能阻止插件在 `onLoad` 内部启动一个定时器，但宿主并不知道它存在，无法上报它，也无法重启它——一次崩溃就会悄无声息地丢掉这项工作。

**插件间消息传递。** SDK 中的 `pi.events.on` / `off` 只是空实现。想要协作的插件只有文件系统可用，而文件系统对宿主不可见且无边界。

两者都需要同样两样东西：让宿主知道插件正在做某事，以及一条父→子的推送通道。插件线上协议只有请求/响应帧（`init` / `call` / `res` / `log`）——每条消息都源自子进程。

## 决策

### 一个新帧

broker 增加一个单向的父→子帧：

```text
{ t: "event", event, ... }   // no reply, no backpressure
```

`bus.message` 是它的第一个使用者。同一个帧最终实现了 `pi.events.on` / `off`，它现在能看到原始事件流。

### 常驻服务

1. 服务是**声明式**的（`contributes.services`，每个插件最多 4 个），并由 `background.service` 门控。子进程中的 `pi.services.register({ id, start, stop })` 仅是本地记账——manifest 已经表明该服务存在，因此注册无法创建一个服务。
2. **broker 决定它何时运行**：在 `onLoad` 完成后调用 `start`（5s 预算），在 `onUnload` 之前调用 `stop`。因此，服务绝不会存在于插件仍持有其 API 的窗口之外。`start` 在单个进程内是幂等的。
3. 服务运行在插件的 `utilityProcess` 中（ADR 0008），所以一次崩溃会随进程一起把它带走。supervisor 重启**整个插件**：退避 1s、2s、4s、8s、16s，上限 30s；最多 5 次尝试；持续运行 60s 的进程视为健康并重置计数器。`autoRestart: false` 可选择退出。
4. 在最后一次尝试之后，插件保持 `failed`。每个服务的状态（`starting` | `running` | `stopped` | `failed`）以及重启次数通过 `plugin/services` 读取，在 Plugins 页面渲染为 chip，并作为 `plugin.service.*` 审计。
5. 手动启用/禁用优先于 supervisor：显式用户操作会取消待执行的定时器并清零尝试计数器。

### 消息总线

1. 流量**在 manifest 中声明**：`contributes.bus.publish` 列出具体主题，`contributes.bus.subscribe` 列出模式。权限 `bus.publish` / `bus.subscribe` 是必要的但不充分——已授予权限但没有声明，就什么都不会被路由。
2. 主题由点分隔的段组成（`[a-zA-Z0-9][a-zA-Z0-9_-]*`，≤8 段，≤128 字符）。`*` 匹配一个段；`**` 匹配一个或多个尾部段，且只能作为最后一个段出现。
3. **路由位于 broker 中。** 消息携带 `topic`、`from`、`payload` 以及宿主分配的 `at`。发布者被排除在自身扇出之外。投递是即发即忘的，因此被卡住的订阅者不会拖住发布者。
4. 上限：每个 payload 64KB，每个插件 16 个订阅，滚动 10s 窗口内 100 次发布；超限调用失败并返回 `LIMIT_EXCEEDED` / `RATE_LIMITED`，并连同主题一起被审计。
5. payload 是**数据，绝非能力**。接收到一条消息不会给订阅者带来它本来没有的东西，因此任何权限都无法经由总线被洗白。

## 影响

- 后台 worker 现在是一等、可见、受监管的东西：用户能看到它运行、看到它重启、看到它放弃。
- 重启插件而不是服务是粗粒度的——一次崩溃会重新执行 `onLoad`——但它是唯一诚实的单位，因为崩溃已经摧毁了服务所栖身的进程。
- 5 次尝试的上限意味着一个真正损坏的服务会停止重试。这正是意图：一个可见的 `failed` chip 胜过烧 CPU 的隐形崩溃循环。
- 声明的主题使插件间的耦合可被评审，并让宿主在不了解任何 payload 语义的情况下拒绝未声明的流量。
- 因为发布者被排除在自身扇出之外，插件无法把总线当作内部事件发射器——它必须使用普通函数调用，而这本来就是它应该做的。
- 任何持有 `bus.subscribe` 且模式匹配的插件都能看到某个主题，因此主题在应用内实际上是公开的。秘密不应放在上面。

## 备选方案

### 让插件自行启动定时器并称之为服务

已拒绝。这就是现状。宿主无法上报、停止或重启它不知道的工作，用户也完全看不到它。

### 就地重启服务而不是插件

已拒绝。服务运行在插件的进程内；如果它使进程崩溃，就没有可供就地重启的进程。为每个服务分配独立进程会成倍放大 ADR 0008 的隔离成本，而在当前规模下毫无收益。

### 无限重启

已拒绝。带退避的崩溃循环仍会永远烧 CPU，并把故障藏在 `starting` 与 `failed` 之间闪烁的 chip 后面。

### 仅靠权限的开放式 pub/sub

已拒绝。那样 `bus.publish` 就意味"与每个插件谈论任何事"，这是无法评审的。声明的主题让 manifest 成为插件所说与所听的完整陈述。

### 直接的插件到插件 RPC

已拒绝。它在可独立安装、独立版本化的插件之间制造硬依赖，并且把一个插件的句柄交到另一个插件手中。主题 pub/sub 让双方互不知晓。
