## 背景

此前的评审实现会基于当前的 Git 工作树重建每张卡片。因此，一次提交会抹去更早的工具消息的证据，而对同一路径的后续编辑可能使旧消息看起来描述了它从未执行过的工作。该模型也无法安全地恢复某条特定消息之前的文件内容。

评审是一项对话功能，因此其证据必须归属于产生它的那条消息，而不是归属于一个可变的仓库快照。

## 决策

1. 在工作区 `Write` 或 `Edit` 之前，主机核心会在工作区之外的会话级快照中捕获该文件此前的字节内容。工具成功执行后，它会将一条有界的 `details.review` 记录写入工具结果。该记录包含快照 id、消息/工具 id、相对路径、操作、新增/修改/删除状态、新增/删除行数、可展开的 hunks、激活/已回滚状态，以及回滚是否可逆。
2. 渲染器仅从持久化的工具消息派生 `InlineReviewCard` 以及评审面板的按时间顺序历史。它绝不刷新或匹配当前的 Git diff。卡片始终紧跟在拥有它的工具行之后，并在提交、切换工作区和重启后仍然可见。
3. `review.rollback({sessionId, snapshotId})` 是由主机拥有的操作。写入之前，主机核心会校验当前文件哈希是否等于快照中记录的工具执行后哈希。不匹配则返回 `conflict`，且不改动文件。匹配则恢复之前的字节内容，或删除该消息创建的文件，然后在工具行上持久化 `state: "rolledBack"`。
4. 快照存储是有界的，并归会话所有：`<data_dir>/review-changes/<sessionId>/<snapshotId>/{before,meta.json}`。删除会话会移除它；启动时会移除已缺失会话对应的目录。分叉的转录记录保留可见的 diff 证据，但标记回滚不可用，因为源快照属于另一个会话。
5. 对 scratch 根目录的写入、失败的工具，以及没有结构化工作区路径的工具都不会创建评审记录。当有界的先前内容无法保留时，大型文件或二进制文件仍可显示状态/计数元数据，但会省略 hunks 和回滚。

## 影响

- 工具执行后再提交，不再使其评审编号或卡片消失。
- 每个可见 diff 都绑定到产生它的确切消息，包括新增、删除和修改。
- 回滚是显式的、幂等的，并拒绝覆盖后续的工作。
- 评审不再承诺描述无关的 shell 变更；结构化的 Write/Edit 结果是持久的评审边界。
- 快照字节会增加主机拥有的本地存储，并受文件与 diff 上限的约束。

## 被否决的备选方案

- **继续读取 Git HEAD：** 提交会抹去证据，且无法识别对同一路径后续编辑负责的那条消息。
- **只存储渲染器补丁：** 渲染器无法安全地恢复文件，而且补丁会在重启或会话重新加载时丢失。
- **无条件回滚：** 它可能覆盖用户后续的编辑或外部变更，因此工具执行后哈希校验是强制性的。
