## 上下文

M5 日志器通过将 app、host 和 agent 输出分别保存在三个轮转文件中，缓解了无界增长问题。但在实践中，正常的会话活动、工具耗时、供应商诊断信息以及生命周期噪声仍然累积在同一个文件里，导致单次故障的排查成本很高。子进程的 stderr 还会以任意大小的块到达，并且 Rust tracing 的颜色被以转义序列的形式持久化。

## 决策

1. 保留 `app`、`host` 和 `agent` 作为顶层本地日志通道，但将每个通道写入一个由聚焦类别文件组成的目录：`logs/<channel>/<category>.log`。
2. 主进程调用点显式声明类别。host 和 agent 的 stderr 使用基于标记的分类；耗时记录始终使用 `timing`，未知输出使用 `runtime`。
3. 在每条 NDJSON 记录中加上类别。日志器按行缓冲子进程 stderr，在流边界处解码 UTF-8，并在写入前剥离 ANSI 控制序列。
4. 对每个类别文件独立应用现有的 5 MB / 两个轮转文件策略。轮转失败和磁盘故障仍然不致命。现有的扁平文件不会被自动删除。

## 后果

- 诊断排查时只需打开相关的会话、工具、耗时、供应商或生命周期流，而不必扫描一个混合文件。
- 耗时记录在稳定路径上仍然易于 grep：`host/timing.log` 和 `agent/timing.log`。
- logs 文件夹中的文件更多了，但每个文件都有确定的大小上限和明确的用途。应用仍然暴露相同的文件夹打开操作。
- 旧的 `app.log`、`host.log` 和 `agent.log` 文件仍可作为历史记录读取，但新记录只会写入按类别划分的布局。

## 被否决的备选方案

- **每个通道保留一个文件，依赖 `category` 字段：** 保留了促使本次变更的扫描问题。
- **每个会话创建一个文件：** 会产生无界数量的文件，并且让启动、供应商和进程故障没有自然的会话归属。
- **在启动时删除或迁移旧文件：** 有丢失诊断历史的风险，并且会让一项日志改进有可能导致应用启动失败。
