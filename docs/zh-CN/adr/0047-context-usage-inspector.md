## 背景

最初的上下文用量环形指示器只展示了一个百分比和一份小型的汇总明细。它无法回答一个回合为何变得很大、哪个工具贡献了最多的上下文，或者模型生成输出的速度有多快。运行时已经拥有供应商用量、工具参数/结果以及模型流计时锚点，但供应商并不暴露精确的按工具分配。

## 决策

1. 将独立的环形指示器替换为一个紧凑的 Codex 风格上下文检查器触发器。*（由 D225 修订：悬停和聚焦不再打开面板；点击或用键盘激活触发器来切换它。）* 激活触发器会显示一个可滚动的非模态面板。
2. 保持供应商上报的输入/输出/缓存/推理用量为权威值，并仅在已完成的回合上以 `outputTokens / responseDurationMs` 展示聚合输出吞吐量；活跃流不渲染实时估算。
3. 使用现有的 pi-agent-core token 启发式方法估算每个工具的参数和结果占用。将估算值持久化到工具消息上，在 UI 中将其标记为估算值，并且绝不将其计入供应商总量。
4. 在助手消息上携带 `responseDurationMs`，在工具消息上携带 `toolUsage`。将 `toolUsage` 作为可选事件字段添加到 `tool_end`，以便实时、持久化和恢复的对话记录使用相同的值。
5. 保持增量兼容性：缺失的字段使用渲染器回退估算，或者在没有可用的流时长时省略吞吐量。
6. 通过 `document.body` 将检查器面板渲染为固定的视口覆盖层。测量触发器和面板矩形，选择有可用空间的一侧，将结果钳制到视口边距内，并在对话记录滚动、窗口尺寸变化或面板尺寸变化时更新位置。保持打开/关闭和 Escape 关闭行为独立于对话记录滚动容器。
7. 按工具的精确名称聚合重复的工具行，并保留首次出现的顺序。每一行显示调用次数，并对这些调用求和参数、结果、token 和已知时长估算值。
8. 从 Electron 传递给代理 sidecar 的同一份 `pi-ai` 模型记录中解析上下文窗口总量，并用该值补充缓存/发现的模型行。仅当所选模型在 `pi-ai` 目录中缺失时，才使用供应商元数据和 128K 默认值。

## 后果

- 用户无需打开日志即可检查精确的模型用量，并看到每种工具类型相对的上下文占用，同时重复调用通过其调用次数保持紧凑且可审计。
- 历史工具行通过确定性的回退估算依然可用。
- 工具估算值是透明的，但不能声称具备计费精度。
- 对话记录协议和存储形态增加了可选字段，同时现有协议版本保持兼容。
- 面板不再受对话记录的溢出裁剪或层叠上下文限制；碰撞感知的放置方式使其完整内容在视口边缘处依然可见。

## 备选方案

- 仅保留环形 UI：被否决，因为它隐藏了大回合的来源。
- 声称精确的按工具供应商用量：被否决，因为供应商响应不包含该归因。
- 通过挂钟回合时间计算吞吐量：被否决，因为工具等待和供应商等待会扭曲模型生成速度。
