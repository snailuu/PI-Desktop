# ADR 0049：以保留尾部的方式恢复自动上下文压缩失败

## 上下文

回合边界上下文防护能正确阻止超大的供应商请求，但在会话已经到达硬边界之后，LLM 摘要请求仍可能失败。把每一次自动摘要失败都视为终止回合，虽能让完整记录持久留存，却会迫使下一条用户消息手动恢复会话。这也使得瞬时的或特定供应商的摘要器故障，与无法持久化检查点之间的界限变得无法区分。

可见记录与面向模型的上下文本就是分离的。因此，即使没有可用的新自然语言摘要，检查点也能保留最近一段供应商可接受的消息尾部。检查点仍必须持久化，并且必须通过同样的硬预算复审；否则供应商请求仍会被阻止。

这还涵盖了最新检查点即为当前记录叶节点这一边界情况。在这种形态下，pi 报告没有可摘要的新历史，但一条新的提示仍可能使保留的尾部变得过大。完整记录是重建更小尾部的来源，同时已有摘要被沿用下去。

## 决策

仅针对自动 `threshold` 与 `overflow` 压缩，PI-Desktop 使用一个具有三种结果的控制器：

1. 对摘要输入在供应商模型窗口下做预检。如果序列化历史加上摘要输出额度无法容纳，就跳过这个注定失败的摘要请求；否则运行常规的 pi-agent-core 摘要压缩。
2. 如果摘要生成失败，或生成的检查点仍高于安全预算，则准备一个确定性的回退检查点。它在可用时复用先前的检查点摘要，添加一个简短恢复标记，保留一段经过激进限界的最近尾部，并记录
   `details.fallback = "retained_tail"`。
3. 通过主机核心追加该回退，并重新估算模型上下文。回退成功会发出带
   `fallback: "retained_tail"` 的 `compaction_end`；当前运行继续进行，渲染器显示警告而非正常的成功提示。

手动 `/compact` 绝不静默回退。持久化追加失败、缺少记录边界，以及仍然超大的回退检查点，都会发出 `CONTEXT_COMPACTION_FAILED` 并阻止受防护的供应商请求。

回退永不删除、重写或替换完整记录。回退只是重启后重建的模型上下文视图。

## 后果

- 当能装入一段安全的持久保留尾部时，自动压缩失败不再终止运行。
- 摘要生成失败时，模型可能丢失较早的任务细节；警告和检查点元数据使这种降级变得显式可见。
- 主机侧持久化与硬预算校验仍为强制要求，因此恢复机制不会以更好的用户体验换取不安全的供应商请求。
- 手动压缩仍是具有快速失败语义的显式用户操作。
- 事件与检查点元数据提供了稳定的诊断信号，同时不会持久化可能包含敏感端点详情的供应商错误文本。

## 备选方案

### 不带检查点继续

被拒绝，因为下一次供应商请求将绕过硬防护，并可能重现供应商上下文上限失败。

### 删除可见记录历史

被拒绝，因为这会破坏可搜索性、诊断能力、分叉输入以及用户的完整对话。

### 无限次重试摘要

被拒绝，因为长时间或不兼容的供应商故障可能让会话无限期处于忙碌状态。有界的确定性回退是可预测的，并且保持供应商请求闸门完好。
