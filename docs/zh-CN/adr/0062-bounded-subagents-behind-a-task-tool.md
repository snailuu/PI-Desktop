# ADR 0062：由 Task 工具承载的受限子代理

> **翻译说明：** 本页是与 [英文源决策](/adr/0062-bounded-subagents-behind-a-task-tool) 一一对应的机器辅助翻译。代码、协议字段和标识符保持原文；如翻译与英文源事实有歧义，以英文版本为准。

## 背景

单个代理循环要为其读取的一切付出代价。大范围搜索、冗长的构建日志和多文件勘察都是可拆分的工作，一旦结论已知，它们的中间输出就毫无价值，然而这些内容全部落入会话的上下文窗口，并在任务的剩余时间里一直留在那里。自动压缩（ADR 0049）能在事后回收空间；它无法避免这些开销的发生。

委派是标准答案：把可拆分的部分放到它自己的上下文中运行，只返回一份报告。将其加入 PI-Desktop 会触及每一层，而待解决的问题不在循环本身，而在于边界——定义从何而来、委派代理可以对工作区做什么、委派代理的行与父级的模型上下文及转写记录之间是什么关系，以及当多个委派代理同时想引起用户注意时会发生什么。

## 决策

### 1. 定义是 Markdown 文档，由内置文档与全局用户文档组成

一个子代理定义由 frontmatter 加上一段 Markdown 正文构成，后者成为委派代理的系统提示词，与提示词模板（D123）保持一致：

```text
~/.agents/subagents/<name>.md
```

PI-Desktop 在 `agent-runtime` 中以内联方式内置三个定义（`explorer`、`code-reviewer`、`test-runner`）。`~/.agents/subagents` 下的用户文档按名称与内置定义合并。不存在项目级的子代理能力来源；全局用户目录是唯一的用户管理层。该目录在每次会话启动时重新读取，上限为 `MAX_SUBAGENT_DEFINITIONS`（16），格式错误的文档降级为一条启动诊断——它绝不会让会话失去其他委派代理或它的回合。

Frontmatter 键：`name`、`description`、`tools`、`model`、`thinkingLevel`、`maxTurns`、`idle-timeout` 和 `max-duration`。键名拼写采用宽松匹配（`max-turns`、`max_turns`、`maxTurns`）。`maxTurns` 是可选的；省略、`none` 和 `0` 均表示回合数不限。超时默认值与边界由 ADR 0119 定义。

### 2. 定义声明其工具，不声明时即为只读

`tools` 只能指定文件、搜索和 shell 工具（`SUBAGENT_ASSIGNABLE_TOOLS`：Read、Glob、Grep、BrowserPreview、Bash、Edit、Write）。插件、技能、模式和元工具都不可及：委派代理是受限的工人，而不是第二个完整会话。省略 `tools` 的定义获得 `Read, Glob, Grep`，而 `tools: "*"` 展开为可分配集合，而不是会话所拥有的一切。委派代理永远不会从父会话继承变更权限——写入能力只来自它自身的声明。

每一次委派代理的工具调用都走与父级相同的 `tools.execute` 主机路径，因此隔离、权限模式和硬性拒绝保持不变。委派代理无法提出父级可以提出的面向模型的问题：不能提交计划或目标，不能切换模式，不能嵌套 `Task`。

### 3. 定义可以固定自身的供应商与模型

`model: <provider>/<model>` 将委派代理绑定到特定模型，与其所在会话的模型无关。固定配置在 Electron 主进程中每次启动只解析一次，因为凭据和 pi 模型目录都在那里，且上限为 `MAX_SUBAGENT_PROVIDERS`（8）个不同的供应商。由于存储的供应商 id 是 UUID，固定配置会按 id、供应商键或显示名进行匹配。

无法解析的固定配置（没有匹配的供应商、没有 API 密钥）会被排除在绑定映射之外，而不是回退到会话的供应商，并且 `Task` 调用会失败，返回一个指名该固定配置的工具错误。一个要求使用廉价模型的定义，绝不能悄悄花掉昂贵模型的钱。

### 4. 委派是一个 Agent 模式工具，且天然并行

`Task` 工具接受 `agent`、`task` 和一个可选的简短 `description`。可用委派代理的目录搭载在工具描述中而非系统提示词中，因为二者总是一起变化。

`Task` 只在 Agent 模式下提供。Plan 和 Goal 是只读的契约协商（D198），而一个拥有 Bash 或 Edit 的委派代理会直接横穿其中。

并发通过 pi 的执行模式来表达：会话 Agent 以 `toolExecution: "parallel"` 运行，每个目录工具都带有 `executionMode: "sequential"`，只有 `Task` 带有 `"parallel"`。pi 只要某批次中包含一个顺序工具，就会顺序执行该批次，因此唯一会扇出的批次是全部由 `Task` 调用组成的批次。现有的工具顺序保证不受影响。扇出由信号量限制在 `MAX_SUBAGENT_CONCURRENCY`（4）以内。委派代理的运行时边界是 ADR 0119 中事件驱动的空闲看门狗与总时长看门狗；按定义显式声明的 `maxTurns` 仍然是一个可选的硬性兜底，上限为 80。

扇出让一个同进程内的顺序问题变得真实，而这个问题由 sidecar 负责。host-core 在同一时刻只允许每个会话有一次变更，因此并发写入不会被撕裂，但它没有定义两个相同路径的变更之间的顺序——而 sidecar 的编辑恢复契约按路径统计失败次数，并会终止对同一文件的第二次失败的 `Edit`，只有在这些尝试是有序的情况下，这才意味着“重新读取并重试一次”。sidecar 中的 `PathMutex` 按规范化路径串行化变更调用；不同路径之间从不互相等待，这正是其目的所在。委派代理还运行在与父级相同的受限供应商重试策略之下（一次重试，8 秒延迟上限），因此一次扇出不会把一个故障中的供应商变成重试风暴。

### 5. 父级上下文只获得报告，且仅限于报告

`SubagentRun` 是同一 sidecar 进程中的第二个 pi `Agent`。它的最终消息被限制在 `MAX_SUBAGENT_REPORT_CHARS`（12k）以内，成为 `Task` 工具结果，并以 `agent`、`status`、`turns`、`toolCalls` 和 `usage` 作为结构化详情。

委派代理的消息和工具行仍会被发出并持久化——它们正是让一次委派可被审查的原因——但每一行都带有 `parentToolCallId` 和 `agentName`，运行时在重建模型上下文时会跳过这些行。重放它们既与父级实际看到的内容相矛盾，又会重新引入委派本应避免的上下文成本。

委派代理的终止——成功、触及上限、超时、失败、中止——都会折叠进工具结果。它永远不会到达 Electron 主进程的回合处理逻辑，因此父级回合仍然是唯一能结束回合的东西。超时策略和 `timed_out` 结果见 ADR 0119。

### 6. 归属信息被持久化，转写记录据此推导其拓扑

host-core 将 `parentToolCallId` 和 `agentName` 存入消息的 `meta` 对象，因此重新加载的会话与实时会话的嵌套结构完全一致。渲染器把每一行带归属信息的行归组到生成它的那条 `Task` 行之下，并把它们缩进一级渲染；回合流和小地图只看到父级的行。报告只打印一次：当委派代理没有产生答案行时打印在 `Task` 正文中，否则作为嵌套的答案行打印。

活动组中的每一次 `Task` 调用都绘制为一份委派摘要，单独一次调用也不例外（D265）。连续出现的 `Task` 起始行是该组中唯一的行（D319）：父级思考、工作区工具和生命周期行都留在卡片周围的普通处理组中。其头部从这些相同的工具消息中推导出代理数量、已结算数量、耗时和聚合状态；其展开后的正文渲染出一层的主代理到委派代理的拓扑。每个委派代理节点保留原来的行展开面板、简要说明、报告、计数器和嵌套步骤。实时扇出在拓扑首次出现时打开一次，此后展开与否由用户控制；重新加载的历史保持折叠。不新增任何图记录、边、IPC 字段或存储 schema：实时与重新加载都从持久化的父级 id 推导出相同的拓扑，UI 永远不会伪造委派代理之间的边，也不会伪造它并不拥有的父级摘要。

### 7. 权限请求按会话排队

渲染器过去每个会话只持有一个待处理的权限请求。并行的委派代理打破了这一点：两个委派代理可能各自都在等待一次 `Bash` 调用。待处理请求变成一个按会话维护的队列，最先到达的排在前面。只有队首可被应答；应答按请求 id 匹配，因此迟到的应答无法清除后继请求；主机端已过期的请求会按工具调用 id 从队列中的任意位置移除；一次中止会拒绝整个队列。卡片会指明是哪个委派代理发出的请求，以及它身后还有多少个请求在等待。

## 备选方案

- **v1 采用串行委派。** 更简单，而且本可以避免路径锁和权限队列。被否决：委派的价值很大程度在于把一次勘察扇出，而事后改造并发将意味着重做转写记录和权限方面的工作。
- **始终继承会话模型。** 推理起来更省事。被否决：大范围搜索恰恰是值得用廉价快速模型去做的工作，而父级继续使用昂贵的模型。
- **让委派代理继承父级的工具。** 被否决：这会让每一次委派都与会话本身一样危险，而定义是读者唯一能看出委派代理可以做什么的地方。
- **每个委派代理一个独立进程。** 真正的隔离，但它会在一个已经运行在 host-core 隔离之下的受限工人身上重复主机连接、供应商配置和事件管线。在 v1 中被否决。
- **把委派代理的行平铺进转写记录。** 被否决：有并行委派代理时，交错的行无法阅读，而且这暗示父级看到了它从未看到的工作。
- **把委派代理的消息回灌到父级上下文中。** 被否决：这正是委派所要去除的成本。
- **把定义放在设置/SQLite 中。** 被否决：定义就是提示词，应保持为磁盘上的 Markdown 文档。ADR 0112 将用户管理的定义放在 `~/.agents/subagents` 下，使它们能跨仓库跟随用户，而无需引入项目能力目录。

## 影响

- 大范围搜索、审查和命令运行搬出了会话的上下文，代价是每次委派多出一份报告。
- 用户可以在 `~/.agents/subagents` 下添加一个委派代理；无需重新构建、无需更改设置，在本地启用后于下一个提示词生效。
- 同一批工具现在存在两个能力面：会话的模式和定义的 `tools` 列表。委派代理可以严格弱于其会话，绝不会更强。
- 权限 UX 必须处理不止一个等待中的请求，这对任何使用并行委派代理的用户都可见。
- 委派代理的行会让磁盘上的转写记录变长；它们保持折叠且不进入模型上下文，但审查和回滚仍能看到它们。
