## 上下文

近期持久化会话显示，模型与原生工具之间反复出现路径形态不匹配。在猜测的
文件名不存在后，`Read` 被传入了一个目录；而 `Grep.path` 虽只接受目录，却被反复传入
单个明确的文件。这些都是可恢复的检查类失误，却被报告为通用的执行失败。

转录记录进一步加剧了问题。失败的工具行正确地保留了自身的错误，而包含它的
活动组也根据任意子错误推导出终态失败。因此，后续成功的搜索与最终回答仍可能
让一个已完成的回合被标记为 `Failed after ...`。

## 决策

1. 保留 D185 的代理核心与延迟工具边界。`Glob` 与 `Grep`
   仍按需加载；当需要列出目录或文件名不确定时，每个新的代理提示词都必须通过
   `ToolSearch` 激活 `Glob`。
2. 强制并公开一份可移植的路径契约：
   - `Read.path` 接受既有的常规文本文件，绝不接受目录。
   - `Glob.path` 接受目录。
   - `Grep.path` 既可接受单个文件，也可接受目录树。显式文件会被直接搜索，
     而 `include` 仍按其 basename 过滤。
3. 传给 `Read` 的目录会返回公开的 `INVALID_ARGUMENT`，而非
   `TOOL_FAILED`。其结果包含 `suggestedTool: "Glob"` 以及有界的
   `suggestedArgs`，其中带有原始路径与 `pattern: "**/*"`，使模型无需猜测即可
   修正调用。
4. 宿主定义、运行时 TypeBox schema、主代理指引与子代理指引承载相同的路径
   语义。子代理不会获得 `ToolSearch`，因此其指引只引用该定义实际可用的
   工具。
5. 工具错误仍在其自身的 ToolCallRow 上可见并自动展开。活动组仅表示处理时长
   与步骤包含关系；它绝不根据子行推断回合的终态失败。终态代理错误、
   TurnOutcomeCard、侧边栏状态与通知仍是唯一的回合结果呈现面。

主机协议与存储 schema 版本均无变更。现有的工具结果本身就是结构化 JSON 值，
而 Grep 的输入形态仍为字符串。

## 影响

- 常见的单文件 Grep 调用不再因仅限目录的契约而失败。
- 误将目录传给 Read 时，会收到可操作、不可重试的纠正，而非含糊的执行失败。
- 已恢复的回合不再显得终态失败，同时原始失败调用在展开的转录记录中仍可审计。
- 延迟搜索保留了 D185 实测的首个请求上下文缩减；提示词必须明确每个用户提示词
  的激活边界。

## 考虑过的替代方案

### 将 Glob 与 Grep 放回代理核心

否决。这会推翻 D185 有界首个请求上下文的决策，而所观察到的失败无需在每个
提示词中加载这两个 schema 也能修正。

### 当 Read 收到目录时静默执行 Glob

否决。这会使被审计的工具名与实际执行的操作不一致，并返回超出 Read 契约的
结果形态。

### 保持 Grep 仅接受目录

否决。直接的文件路径含义明确，比遍历其父目录开销更小，并且在各类编码代理
工具约定中都很常见。

### 在回合结束后将活动组标记为失败

否决。回合结束并不意味着每个中间工具调用都成功；专门的终态结果呈现面已经
负责回合失败。
