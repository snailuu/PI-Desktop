# ADR 0077：新增交互式多问题 asktool

> **翻译说明：** 本页是与 [英文源决策](/adr/0077-asktool-interactive-multi-question-flow) 一一对应的机器辅助翻译。代码、协议字段和标识符保持原文；如翻译与英文源事实有歧义，以英文版本为准。

- 状态：已接受实施
- 日期：2026-08-12
- 决策者：PI-Desktop core
- 相关：E2E-123

## 上下文

模型需要一种结构化的方式来收集若干用户决策，而不必将其转化为聊天文本或权限审批。用户可能一次回答一个问题、选择多个选项、提供自定义文本、跳过某个问题，或拒绝整个提示。即使未作答，也需要一个稳定的工具输出，使模型能够将其与缺失的工具结果区分开。

## 决策

1. 为每种操作模式添加内置的 `asktool`。它会发出一个带类型的 `asktool_request` 事件，并暂停运行时，直到渲染器通过 `pi-desktop/agent/askTool/resolve` 解析该请求。
2. 该请求携带一个有序的问题文本数组、选项标签，以及一个可选的多选标志。无论模型给出的选项列表如何，渲染器始终提供一个自定义文本输入选项。
3. 渲染器持有草稿选择状态，并一次显示一个问题。跳过和拒绝解析为 `null`；答案数组携带已选标签和自定义文本。该卡片挂载在 Plan 与 Goal 审批共用的输入框审批界面中。asktool 没有超时或过期机制。
4. 运行时将解析后的值格式化为普通工具内容：每行格式为 `question：answer`，多个问题之间使用 `\n---\n` 分隔，null 答案在分隔符后使用空值。

## 后果

- 模型收到的是确定且紧凑的工具结果，而不是 UI 状态。
- 交互式等待不属于宿主权限策略的范围，并且无法授予工作区能力。
- 该请求是对现有代理事件信封的增量扩展，无需提升协议版本。
- 中止一个回合时，会以跳过值完成尚未结束的工具调用，因此待处理的卡片不会让运行时陷入停滞。
