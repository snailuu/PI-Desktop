# ADR 0080：启动后预热全局插件启动器

> **翻译说明：** 本页是与 [英文源决策](/adr/0080-prewarm-global-plugin-launcher) 一一对应的机器辅助翻译。代码、协议字段和标识符保持原文；如翻译与英文源事实有歧义，以英文版本为准。

- **相关：** D211 · D217 · ADR 0072 · E2E-120

## 上下文

全局插件启动器此前是在首次通过 Option/Alt+Space 调用时惰性创建的。该路径必须分配第二个 Electron `BrowserWindow`、启动其沙箱化渲染器、加载共享渲染器 bundle、挂载 React，然后才能显示启动器。因此，即使窗口在使用后会被保留，首次调用仍明显比后续调用更慢。

## 决策

一旦 Electron 就绪，在后端/插件启动完成之前，Electron 就开始在后台创建并加载启动器窗口，同时保持其隐藏。该工作与主启动流程并行运行。快捷键调用仍会为同一个被保留的窗口设置当前显示器边界、显示并聚焦。

窗口创建由一个共享的进行中 promise 表示。在预热仍在加载期间收到的快捷键会加入该 promise，从而避免出现空白窗口、丢失 shown 事件或重复创建渲染器。预热失败会被记录日志、销毁不完整的窗口、清除该 promise，并让正常的快捷键路径仍能重试创建。

启动器在每次显示时仍会刷新插件目录，因此预加载改变的是呈现延迟，而不会使插件可用性变为陈旧，也不会改变 IPC、主机 RPC、权限、协议 v9 或存储 schema v11。

## 后果

- 启动后的首次快捷键不再在其可见路径上承担 BrowserWindow 和渲染器加载延迟；预热启动得足够早，可以与后端启动重叠。
- 启动后仍会驻留一个隐藏的沙箱化渲染器，以有界的内存开销换取一致的启动延迟。
- 应用启动不会被启动器预热阻塞，并且预热失败也不会阻止后续快捷键重试。

## 考虑过的替代方案

- 保留首次使用时惰性创建：可保持最小的空闲占用，但会保留所报告的首次启动延迟。
- 将预热作为应用启动的一部分进行等待：可保证在应用被标记为已启动之前就绪，但会延长主窗口的关键启动路径。
- 复用主渲染器：可避免第二个渲染器，但在 PI-Desktop 未聚焦时无法提供独立的系统级实用程序窗口。
