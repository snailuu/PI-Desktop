## 上下文

ADR 0068 将 `Cmd/Ctrl + J` 定为仅打开的动作，并否决了切换方案，理由是面板头部已经承担了收起职责，而且切换可能在用户想要展开面板时反而把它隐藏。在实际使用中，这种不对称给人的感受是快捷键坏掉了，而不是一种保护：展开面板的那组按键在第二次按下时毫无反应，因此以键盘操作优先的用户不得不转用头部控件来收起面板。其他所有绑定组合键的外壳界面（`Cmd/Ctrl + B` 对应侧边栏）都是切换式的。

0068 所要防范的误隐藏风险很小，因为该快捷键是对称且可立即撤销的：保留的上下文、标签页、活动资源以及已提交的宽度在收起后都会保留，因此误按一次只要再按一次即可撤销。

## 决策

1. `openWorkPanel` 改为切换。当可见的工作面板处于打开状态时，快捷键通过与头部收起控件相同的路径将其收起；当它处于关闭状态时，快捷键以已提交的宽度展开当前会话保留的上下文，且不创建资源标签页。
2. 通过快捷键收起时会像头部控件一样精确保留会话的上下文 —— 标签页、活动资源、Browser 资源以及已提交的宽度都会保留，因此再次按下即可恢复先前的界面。
3. 快捷键 id 保持 `openWorkPanel`，以便现有的用户按键绑定覆盖继续生效；只有 设置 → 快捷键 中的标签改为描述切换行为。
4. 0068 中关于无活动会话以及 设置 场景下不执行任何操作的上下文保持不变，由工件驱动的资源创建、会话归属以及后台事件隔离同样保持不变。不会新增任何主机协议、IPC 通道或原生应用菜单命令。

## 后果

- 一组按键既能展开也能收起工作面板，与侧边栏保持一致。
- 头部收起控件仍为指针操作用户保留，现在它是指向同一 store 操作的两个等价入口之一。
- ADR 0068 中“将 `Cmd/Ctrl + J` 改为切换”这一被否决的备选方案不再成立；0068 的其余条款仍然有效。

## 备选方案

### 保持仅打开，并新增一个单独的关闭快捷键

否决。新增第二个绑定会把稀缺的组合键空间花在现有快捷键的逆操作上，而且仍然会让第一个快捷键显得没有响应。

### 仅在面板没有标签页时才切换

否决。依赖不可见标签页状态的行为不如纯粹的切换可预测，而且由于上下文会被保留，收起一个有内容的面板本来也不会造成破坏。
