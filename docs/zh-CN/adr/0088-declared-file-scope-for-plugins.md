# ADR 0088：插件文件访问按模式声明，删除操作可恢复

## 背景

ADR 0008 把插件主代码放进它自己的 `utilityProcess`，但指出该进程是一个完整的 Node 环境：权限管控的是 `pi.*` 表面，而不是 `require("node:fs")`。能力沙箱仍是尚未完成的那一半（ADR 0008，D009）。在它落地之前，`pi.*` 关卡就是约束一个规矩插件的东西，也是评审可以依据的东西，因此它的粒度就是整个设计的全部。

而这种粒度只有三个工作区级开关：

- `fs.read.workspace` → 工作区中的任意文件，包括 `.env` 和 `.git/config`
- `fs.write.workspace` → 工作区中的任意路径
- `fs.delete.workspace` → 带 `recursive: false` 的 `fs.remove`，它约束的是一次调用，而不是影响范围：`fs.glob("**/*")` 再配一个循环，清空工作区的彻底程度和 `rm -rf` 一样

两个实现缺陷让情况比设计所承认的更糟。隔离性检查是一次词法前缀比较，所以工作区内一个指向 `~/.ssh` 的符号链接就能满足它；并且运行时会回退到 `grantedPermissions ?? manifest.permissions`，也就是说只要调用方省略了授权参数，manifest 申请的一切都会被自动授予。

`07-plugins/13-plugin-permissions-matrix.md` 一直为这些权限规定的是“首次使用时确认”/“每次或按会话确认”。这些都没有实现。下面的收窄正是把该 spec 交付出来，而不是一个新方向。

收紧不可能是全部答案，因为一个只能读取的插件系统不值得安装。风险并不对称，应对方式也不应对称：

- **读取**在字节可以外泄时才危险。这一半由出站允许列表（`manifest.net.domains`）单独封住，它把面板会话、`pi.net.fetch` 和远程 MCP 端点都限制在已声明的主机名内。出站被封住之后，宽泛的读取就是一个小得多的问题。
- **写入**本身就是危险的，损害的大小取决于它能落到哪里。
- **删除**本身就是危险的，而且与前两者不同，它不可恢复——除非删除进入操作系统的回收站，那样它就完全可恢复，危害不高于一次写入。

## 决策

### 1. `manifest.fs` 声明范围；权限名保持扁平字符串

`permissions` 仍是 `readonly string[]`，并新增 `fs.read`、`fs.write`、`fs.delete`——“这个插件是否可以碰文件”。单独的 `fs` 块说明“碰哪些文件”：

```json
{
  "permissions": ["fs.read", "fs.write", "fs.delete"],
  "fs": {
    "read": { "root": "workspace", "scope": ["**/*"] },
    "write": { "root": "workspace", "scope": ["docs/**", "*.md"] },
    "delete": { "own": true, "scope": ["dist/**"] }
  }
}
```

之所以用单独字段，而不是把对象放进 `permissions`，是因为权限在端到端各处都按字符串处理——安装评审、权限标签、授权往返、目录校验——而插件市场目录格式是另行版本化的。

`fs.read` 可以声明整棵树；`fs.write` 和 `fs.delete` 不可以，整树模式（`**`、`**/*`、`*/**`、`./*`）会在校验阶段被拒绝。缺失或为空的 scope 不算错误：它意味着插件没有常驻的访问范围，每次访问都要落到用户身上。

### 2. 四道关卡，顺序固定

每次 `pi.fs.*` 调用按顺序通过：

1. `assertPermission`——`fs.<mode>` 是否被声明**且**被授予（取交集，因此被撤销的权限确实会停止生效）
2. 隔离性——对根路径和目标路径都做 `realpath`；对于正在被创建的路径，对最近的已存在祖先做 `realpath`。越出根路径的符号链接在这里失败，而单纯不存在的路径会报告 `NOT_FOUND`，而不是被当成越权尝试
3. 无条件拒绝列表——在每种根、每种 scope、每种授权下都拒绝凭据和历史：`.env*`、`.npmrc`、`.netrc`、`.git-credentials`、`id_rsa*`、`*.pem`/`*.p12`/`*.pfx`/`*.keystore`，以及 `.git`、`.ssh`、`.aws`、`.gnupg`、`.kube`、`.docker` 内的任何内容，再加上主机自身的数据目录（供应商密钥、会话存储）
4. 已声明的 scope，否则征求用户同意

`pi.fs.glob` 遵循同样的规则：结果按读取 scope 过滤，被拒绝的路径和保留目录会被略去（一个名字也是一次读取），并且 `node_modules` / `.git` / `.venv` / `__pycache__` 根本不会被遍历。

### 3. 删除有两档，且始终进入回收站

- **带 `own: true` 的 `fs.delete`**——主机把每次成功的 `fs.writeText` 追加到插件自身数据目录中的写入账本（路径加 mtime，由主机所有，插件 API 无法触达）。账本中的路径可以无需 scope、无需提示即被删除：清理自己的输出不会让任何人意外。如果文件的 mtime 已经晚于记录的 mtime，说明用户此后动过它，它就不再是该插件的了——删除落到征求同意这一档。
- **带 `scope` 的 `fs.delete`**——删除别人的文件需要事先声明 glob，并且这些 glob 会在展示权限的地方展示给用户。

两档都还要：

- 走 `shell.trashItem`，绝不走 `rm`。这正是让整条删除路径可承受的兜底：上面任何一道关卡出错，用户都不会丢失数据
- 保留 `recursive: false`；非空目录会被拒绝，而不是被清空
- 受一个每插件每 60 秒 50 次删除的滚动刹车约束。超过之后，用户会被询问一次，理由是“这么多、这么快”，而不是被要求去裁决单个文件。这是把清理例程和抹除区分开来的唯一东西

### 4. 同意是一个原生对话框，且绝不超过会话的持久度

超出 scope 的访问会调用 `dialog.showMessageBox`：**拒绝** / **允许一次** / **本会话允许**。会话授权覆盖所在目录，并随进程消亡；什么都不会被持久化。速率刹车提示完全不提供会话选项。没有同意服务的主机一律拒绝——无法询问的主机不得假定为同意。

### 5. `root: "userSelected"`

`pi.fs.requestDirectory()` 打开原生目录选择器并返回一个句柄。在该目录内，插件不需要任何 manifest scope——用户刚刚指向了它，这**就是**授权——同时隔离性和拒绝列表仍然适用。该句柄仅存在于内存中，随进程消亡。

能力在这里回来了。“整理我的整个照片文件夹”、“批量导入/导出”这类插件可以在**零常驻权限**下成为可能，参照浏览器的 File System Access API。

### 6. 迁移是一次破坏性降级

| 旧权限 | 它现在的实际价值 |
|---|---|
| `fs.read.workspace` | `fs.read`，`scope: ["**/*"]`——不变，因为出站已被封住 |
| `fs.write.workspace` | `fs.write`，scope 为空——每次写入都询问用户 |
| `fs.delete.workspace` | `fs.delete`，`own: true`——只有它自己的输出无需询问即可删除 |

能力被削减了；没有留下任何敞口。显式规则总是胜过旧默认值，因此作者是通过添加 `fs` 来升级，而绝不是通过重命名任何东西。插件页面会标记被降级的插件，让用户知道它为什么停止工作、作者需要做什么。

## 后果

- 在已声明 scope 之外写入或删除的插件现在会弹出提示，用户拒绝的提示会被审计为 `PERMISSION_DENIED`。从未声明 scope 的作者会看到写入失败，直到他们声明为止。
- 早于 `manifest.fs` 的已安装插件在下一次加载时失去写入和删除的访问范围。这是有意的，而且是可见的，不是静默的。
- 读取仍然宽松，这使那些有意思的插件仍然可能。这是对出站允许列表的一次押注：如果出站被重新打开，读取 scope 就必须重新审视。
- 在 Electron 支持回收站的每个平台上，删除都可通过操作系统回收站恢复，而我们不为此存储用户的任何数据——没有隔离副本，没有撤销日志。
- 速率刹车是按插件滚动计算的，因此一次合法的大规模清理只被打断一次，而不是被拒绝。
- 这些都不约束**恶意**插件，它仍然可以直接调用 `require("node:fs")`。它约束的是一个插件通过它本应使用的 API 能做什么，并给评审提供了具体的可读内容。恶意情形仍属于 ADR 0008 D009——插件进程内部的能力沙箱——是本条工作线上的下一项。

## 考虑过的替代方案

- **用主机自有的隔离目录加撤销 UI**替代操作系统回收站：已否决。这意味着在应用存储内复制并保留用户的文件，以提供一条操作系统已经提供的恢复路径。
- **把对象放进 `permissions`**（`{ "name": "fs.write", "scope": [...] }`）：已否决。权限在安装评审、授权往返、注册表和插件市场目录中都是字符串；这一改动会波及所有这些地方，只为表达一个用兄弟字段就能干净表达的东西。
- **每次文件访问都提示，不使用 manifest scope**：已否决。同意疲劳会演变成一揽子批准，而一个合法地写入 40 个文件的插件会变得不可用。
- **保留 `recursive: false` 作为唯一的删除约束**：已否决。它约束的是一次调用，不是循环，而速率刹车正是为了抓住循环而存在。
- **彻底拒绝 `fs.write`，只提供插件自己的数据目录**：已否决，因为太狭窄——导出或格式化插件必须能够把文件放到用户要求的位置。
