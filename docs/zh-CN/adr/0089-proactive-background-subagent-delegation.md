# ADR 0089：主动式后台子代理委派

## 上下文

ADR 0062 把委派作为上下文经济性手段交付：`Task` 运行一个委派代理直至完成并返回其报告，工具描述则告诉模型，只有当大范围搜索或长时间调研会填满父级上下文时才进行委派。但在实践中，主代理几乎从不委派：

- 系统提示词完全没有提及委派，因此模型只能看到该工具的防御性描述（“不要委派你几次工具调用就能完成的工作”），没有任何可据以行动的正向触发模式。
- `Task` 会阻塞父级的工具循环，直到委派代理结束，因此在模型看来，委派只是用一项长任务换另一项长任务；委派代理运行期间无法继续工作。
- 所有内置委派代理都是只读的报告机器，因此没有可用于承接实现工作的对象，而具备写入能力的委派代理会在触碰每个文件时触发会话的权限提示。
- 并发上限（4）与即发即忘的契约，没有为诸如“提交前审查我的改动”或“并行探索三个方向再收敛”之类的编排模式留出空间。

## 决策

将委派打造为一等的、主动式的编排能力，同时保留 ADR 0062 确立的每一道隔离边界。

### 1. 委派代理生命周期是非阻塞且由工具驱动的

`Task` 在后台启动委派代理并立即返回一个 `delegationId`。三个新的 Agent 模式工具驱动该生命周期，它们与 `Task` 一并属于核心工具集：

- `TaskWait(delegationIds?, mode?, minCompleted?, timeoutSeconds?)` 对正在运行的委派进行收敛（默认为全部）并返回其报告；`mode: "any"` 加 `minCompleted` 会在前 N 个完成后立即收敛，而已完成的委派会立即返回，因此报告可以按 id 重新读取。
- `TaskList()` 报告会话的委派及其状态。
- `TaskStop(delegationIds?)` 停止正在运行的委派；被停止的委派读作 `stopped`。

会话运行时拥有一个委派注册表（id、agent、状态、计时、结果、完成 promise、中止句柄）。已完成的记录会在会话内保留（上限 100），以便 `TaskWait` 无需重新运行委派代理即可重新读取报告。正在运行的委派会在运行结束时（`agent_end`）、父级中止时或运行时被释放时中止；系统提示词指示模型在结束回合前先收敛或停止委派。

### 2. 系统提示词点明正向触发模式

基础提示词新增一个 `## Delegation` 小节（仅在目录非空时出现），列出具体情形：独立方向的并行探索、提交前的对抗式审查、通过 `fixer` 进行多文件实现、为节省上下文而做的搜索，以及批处理分片——外加收敛规则（在 `Task` 之后继续工作、为用户填写 `description`、绝不在仍有委派运行时结束回合）。`Task` 的描述被重写为以这些触发条件开头，并将原有的“不要”清单保留为单行边界说明。

### 3. 新内置项：更快的 `explorer` 与具备写入能力的 `fixer`

`explorer` 已按 omo-slim explorer 提示词的风格重写：工具选择指引（Grep 用于模式匹配、Glob 用于发现、Read 用于读取文件）、并行搜索，以及结构化的 `<files>` / `<answer>` 报告形态。

第四个内置项 `fixer` 依据完整规格实现多文件改动：`tools: [Read, Glob, Grep, Edit, Write, Bash]`、`maxTurns: 40`，报告形态为 `<summary>` / `<changes>` / `<verification>`。它是唯一具备写入能力的内置项；其余三个保持只读。

### 4. 定义可声明权限范围

Frontmatter 新增 `permission: inherit | ask | accept-edits | auto`（默认 `inherit`）。带有显式非 `inherit` 范围的定义会使 sidecar 将该范围附加到委派代理的 `tools.execute` 调用上，host-core 会按该模式而非会话的有效权限模式来解析每一次调用。省略该范围或其为 `inherit` 时不携带任何覆盖，因此该调用使用父会话的有效模式。该覆盖仅针对权限模式：契约模式的硬拒绝与外部路径门禁仍然有效，因此 `accept-edits` 会自动放行工作区与临时根目录内的 `Write`/`Edit`，而 Bash 与外部路径仍保持会话原有行为。内置的 `fixer` 使用默认的 `inherit` 范围；显式范围仍可用于符合条件的内置定义与用户定义。

### 5. 并发

`MAX_SUBAGENT_CONCURRENCY` 变为每会话同时运行上限 10（此前是每批次上限 4）。当会话已在运行 10 个委派代理时，`Task` 会以工具错误失败，并提示模型先等待或先停止。

## 后果

- 委派不再只是“一次长时间的工具调用”，而成为后台编排：父级可以在 `explorer` 搜索、`code-reviewer` 审查的同时进行实现，随后用 `TaskWait` 收敛。
- 模型在系统提示词中获得正向触发模式和完整的生命周期词汇，这正是让委派变得主动、而非“被允许却从未使用”的关键。
- 具备写入能力的委派代理由其定义中的 `permission` 范围加以约束，而不是由会话的提示来约束；host-core 仍然是权威，外部路径门禁保持不变。
- 旧记录仍可正常渲染：`Task` 行保留其委派分组，新工具映射到相同的委派呈现方式。
- 寿命超过其所在回合的委派会被停止，而不会被放任继续运行；提示规则加上回合结束时中止，使其成为例外而非常规策略。

## 考虑过的替代方案

- **跨回合的后台任务（Proma 风格）。** 让委派在父级回合结束后继续运行、并在 UI 中显示待处理的后台工作，可以最大化并行度，但这需要重构 Electron 主进程的回合生命周期、完成语义以及渲染器的会话空闲处理。回合内的后台委派以不改动现有回合模型的方式，实现了该模式所追求的“父级继续其主线”行为。
- **让委派代理继承会话权限模式。** 已否决：需要 `auto` 的委派代理要么会静默地重新触发权限提示，要么迫使整个会话切到 `auto`；按定义设定的范围使这种放宽保持显式，并可在定义文档中审阅。
- **保持 `Task` 阻塞并增加一个 `wait` 标志。** 已否决：需要模型记得设置的标志，就是模型会忘记的标志；用相互独立的工具构成的生命周期，使“启动、工作、收敛”成为模型可以遵循、提示词可以教授的序列。
