# ADR 0091：通过有界的同回合重试处理供应商速率限制

> **翻译说明：** 本页是与 [英文源决策](/adr/0091-rate-limit-same-turn-retry) 一一对应的机器辅助翻译。代码、协议字段和标识符保持原文；如翻译与英文源事实有歧义，以英文版本为准。

- 状态：已接受
- 日期：2026-08-14（2026-08-19 修订）

## 上下文

供应商返回的 HTTP 429 是暂时性的，但它既可能发生在响应建立之前，也可能发生在流已经开始之后。旧实现把这些情况拆分给 pi-ai 的一次建立阶段重试和运行时的一次流中重放。这会让那些虽然持续但仍可恢复的速率限制过早暴露给用户，并使实际重试预算取决于失败发生在哪个阶段。

OpenCode 的会话重试策略提供了行为参考：速率限制以静默方式重试且设有有限上限，供应商的重试头优先于客户端退避，等待可被中止，且只有在重试耗尽时才渲染失败。PI-Desktop 必须在保持一致行为的同时，不引入 OpenCode，也不通过 pi-ai 自身的包装层放大重试次数。

## 决策

1. `PROVIDER_RATE_LIMITED` 拥有一份运行时重试预算：在最初的供应商尝试之后可进行五次重试。该预算由请求建立与流恢复共享，因此无论 429 出现在哪个环节，一个回合最多只有六次供应商尝试。此路径下 pi-ai 的嵌套重试被禁用。
2. 每次 429 重试都是静默且可中止的。延迟优先级依次为 `retry-after-ms`、`retry-after` 秒数、`retry-after` HTTP 日期，最后是以 2 秒起步、最多带 25% 正向抖动的 OpenCode 风格指数退避。来自服务器的延迟或计算出的延迟一律上限为 30 秒。运行时从底层 fetch 捕获状态与响应头，因为 pi-ai 的正常响应回调不会暴露失败的响应。
3. 流开始之前的 429 由供应商流适配器重试。流开始之后的 429 由运行时在从模型上下文中移除失败的助手消息后重放。两条路径使用同一个控制器和同一份预算。在两个阶段中，都会先应用捕获到的响应状态，再对供应商消息进行分类，因此通用的 429 响应体仍会进入 429 预算，而已知不可重试的分类仍保持终止状态。主会话和每个内置子代理都使用此策略。
4. 中间态的助手错误、生命周期结束事件以及重复的助手气泡都会被抑制。恢复后的尝试复用原本可见的助手消息 id，并且只发出一次终态生命周期事件。失败的尝试不会被持久化到下一次模型上下文中。
5. 认证、模型选择、请求格式错误、上下文以及其他不可重试的失败不会进入 429 路径。既有的非 429 暂时性行为仍单独受限：一次建立阶段重试和一次流中重放。
6. 第五次 429 重试失败后，常规的助手错误与生命周期错误各发出一次。诊断信息保留已脱敏的供应商错误、`phase`、`providerStatus`、有界的等待/计时字段，以及 `retryAttempt: 5`。在等待期间中止会取消定时器并阻止后续的供应商请求。

## 后果

- 短暂的供应商速率限制突发可以恢复，不会出现错误卡片、toast 或需要人工操作，无论 429 出现在建立阶段还是流式传输阶段。
- 持续的速率限制仍受边界约束：总共六次尝试、最多五次退避，单次等待最长 30 秒。最终失败仍然可见且可操作。
- 来自 OpenAI 兼容网关等供应商的重试头会被遵循，同时格式错误或过大的值无法让一个回合无限期挂起。
- 主会话与子代理不会各自漂移出不同的速率限制策略，生命周期消费者会收到一个连贯的助手回合。

## 备选方案

- 保留 pi-ai 的建立阶段重试并再增加一次运行时重试。已拒绝：嵌套包装会成倍放大尝试次数，并使预算依赖于阶段。
- 对每个供应商失败都重试五次。已拒绝：凭据、模型 id、格式错误的请求以及上下文溢出并不会因为重复而得到修复。
- 保留一次同回合重试并依赖 UI 的人工操作。已拒绝：这会让暂时的 429 过早暴露，并且违背了在供应商边界上所要求的 OpenCode 风格行为。
