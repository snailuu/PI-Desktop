# ADR 0094：每个数据目录只允许一个桌面实例

> **翻译说明：** 本页是与 [英文源决策](/adr/0094-single-instance-per-data-directory) 一一对应的机器辅助翻译。代码、协议字段和标识符保持原文；如翻译与英文源事实有歧义，以英文版本为准。

- 状态：已接受
- 日期：2026-08-18
- 决策者：PI-Desktop 核心
- 相关：D236、D002、D216、ADR 0078、ADR 0090

## 上下文

此前没有任何机制阻止第二个 PI-Desktop 进程启动。在应用已在运行时再次启动它——Windows 或 Linux 上的双击、macOS 上的 `open -n` 或在开发宿主旁启动打包后的应用，又或者用户以为已经退出、实际仍驻留在托盘中的会话——都会启动一个完整的第二份副本：同一个 `pi.sqlite` 上的另一个 host core、同一数据目录中的另一个持久化 outbox 和日志树、另一个代理 sidecar、另一个托盘图标、另一次全局启动器快捷键注册，以及另一个更新器。

host core 独占 SQLite（D002）正是为了确保只有一个写入方。第二个应用进程破坏了这一点：两个外壳在同一个数据库之上显示出不一致的会话列表，启动器快捷键的第二次注册会静默失败，退出其中一个还会拆除另一个正在使用的状态。用户的心智模型是一个桌面应用；唯独进程模型与此不一致。

不可共享的是数据目录，而 Electron 的单实例锁作用域是 `userData`，并非 `PI_DESKTOP_DATA_DIR`。指向各自数据目录的运行实例——E2E 测试框架、采集装置、以及刻意并行的配置文件——与默认安装不共享任何状态，必须能在另一个实例运行时继续启动。

## 决策

1. Electron 主进程在模块求值期间调用 `app.requestSingleInstanceLock()`，位置在 `app.setName` 之后（锁文件位于由名称派生的 `userData` 路径下），并且早于任何对数据目录的读写。
2. 未获得锁的启动会立即调用 `app.quit()`，不启动任何东西。就绪处理器和关闭处理器对它都提前返回，因此它绝不会创建窗口、托盘、子进程，也不会在运行中实例的数据目录里写入日志行。
3. 持有锁的实例通过 `second-instance` 处理请求，经由与托盘“显示”动作相同的路径恢复并聚焦其主窗口，该路径会重建已被关闭或隐藏到托盘中的窗口。
4. 仅当 `PI_DESKTOP_DATA_DIR` 未设置时才请求该锁。被赋予了自身数据目录的运行实例保持当前随时可启动的行为。

## 后果

- 一个安装就是一个进程：一个 host core、一个 SQLite 写入方、一个 outbox、一个托盘、一个启动器快捷键绑定、一个更新器。
- 重新启动应用是回到隐藏到托盘或已关闭窗口的可靠方式，与托盘、Dock 以及 `did-become-active` 并列（ADR 0078、ADR 0086）。
- E2E 测试框架、采集装置和并行配置文件不受影响，因为它们设置了 `PI_DESKTOP_DATA_DIR`。
- 两个运行实例指向*同一个*显式数据目录时仍会被允许。这种组合是刻意行为，而非意外重启，并且把锁作用域限定到它意味着将 `userData` 迁移到数据目录之下，并舍弃每个配置文件用户的渲染器本地状态。

## 替代方案

### 将 `userData` 迁移到 `PI_DESKTOP_DATA_DIR` 下

这样做会把锁的作用域限定到真正无法共享的资源上。被否决，因为 `userData` 还保存着渲染器的 `localStorage`（保留的项目标签页和侧边栏呈现，D093）、插件面板分区以及浏览器窗格 Cookie；迁移它会为了封闭一个罕见边界情况而静默丢弃现有配置文件用户的这些状态。

### 在数据目录中保留一个锁文件

被否决，因为它重新实现了 Electron 已提供的功能，而且仍然没有通道来唤起正在运行的窗口；崩溃后残留的锁文件还会在没有任何恢复路径的情况下阻塞应用。

### 让第二次启动聚焦第一个实例并保持存活

被否决，因为驻留的重复实例会毫无意义地保留第二个 Electron 进程、托盘和快捷键注册。立即退出得到相同的可见结果，且没有这些代价。

### 什么都不做，只记录该风险

被否决，因为该故障是在单写入方数据库之上静默发生的数据分歧，而用户没有任何信号表明有两个外壳在同一个工作区上打开。
