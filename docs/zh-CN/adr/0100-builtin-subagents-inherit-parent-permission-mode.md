# ADR 0100：让内置子代理继承父级权限模式

> **翻译说明：** 本页是与 [英文源决策](/adr/0100-builtin-subagents-inherit-parent-permission-mode) 一一对应的机器辅助翻译。代码、协议字段和标识符保持原文；如翻译与英文源事实有歧义，以英文版本为准。

## 上下文

主动委托决策曾为内置 `fixer` 指定了显式的 `permission: accept-edits` 作用域。这使得当父会话处于 `ask` 时，工作区内的 `Write` 和 `Edit` 调用变得方便，但它同时也替换了父会话对所有其他调用的有效权限模式。因此，在设置为 `auto` 的父会话中，`fixer` 调用 `Glob` 或对会话工作区之外的显式路径执行 `Write` 时，会弹出权限卡片，尽管 `auto` 本应允许该路径。卡片正确地识别出请求来自 `fixer`；不正确的地方在于该内置代理意外地采用了更窄的覆盖。

外部路径门控仍然是有意设置的能力边界。权限模式才决定该边界是否需要卡片，而用户自有定义上的显式作用域必须保持有意义。

## 决策

内置子代理定义使用默认的 `permission: inherit` 行为。内置 `fixer` 不再声明 `permission: accept-edits`；其可用工具仍为 `[Read, Glob, Grep, Edit, Write, Bash]`，其工作区/路径包含规则不变。

在没有作用域附加到委托的 `tools.execute` 调用时，主机核心会在父会话的有效权限模式下解析该调用：

- `ask` 对高风险调用和显式外部路径调用保留审批；
- `accept-edits` 仅自动允许根目录内的 `Write`/`Edit`，并保留其他审批边界；
- `auto` 自动允许父会话可以执行的相同调用，包括显式外部路径。

在符合条件的内置或用户子代理上显式声明的非 `inherit` 作用域仍然是刻意的覆盖。项目定义仍然不能使用权限声明来提升到超出会话模式的权限。

## 后果

- 处于 `auto` 的父会话可以使用内置 `fixer`，而不会出现意外的子代理授权卡片。
- 处于 `ask` 或 `accept-edits` 的父会话不会因委托而被静默变得更宽松。
- 内置 fixer 在 `ask` 下可能会为其写入操作弹出提示；需要不同姿态的调用方可以使用显式的用户定义作用域。
- 主机核心的外部路径包含和权限评估不需要特殊子代理例外。

## 考虑过的替代方案

- **将 `fixer` 保持在 `accept-edits`：** 拒绝，因为它会重现观察到的 auto 模式弹窗，并使内置委托忽略用户所选择的权限姿态。
- **将 `fixer` 改为 `auto`：** 拒绝，因为即使在父会话为 `ask` 时，它也会绕过审批。
- **当父会话为 `auto` 时忽略所有委托作用域：** 拒绝，因为用户自有的显式 `ask` 作用域是刻意的更严格策略，必须保持可强制执行。
