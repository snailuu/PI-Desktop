# ADR 0101：模型感知的图片附件传输

> **翻译说明：** 本页是与 [英文源决策](/adr/0101-model-aware-image-attachments) 一一对应的机器辅助翻译。代码、协议字段和标识符保持原文；如翻译与英文源事实有歧义，以英文版本为准。

- 状态：已接受
- 日期：2026-08-18
- 决策者：PI-Desktop 运行时与桌面 UI 维护者
- 修订：D197、ADR 0059、ADR 0070

## 背景

剪贴板图片此前可以成功落地，但输入框会把每个文件都简化为 `@<path>` 文本。因此，一个支持图片输入的模型收到的是文件系统引用，而不是图片内容块。能力信号必须由 pi-ai 用于序列化供应商请求的同一个模型目录来提供；渲染器侧的发现结果以及用户手输的模型 id 都不足以作为依据。

## 决策

1. 保持输入框草稿紧凑且为文本形式。每个文件引用都以结构化元数据的形式保留其种类、名称、MIME 类型和源路径；可见的 textarea 中永远不包含粘贴的二进制数据。
2. 视觉能力必须从精确的 pi-ai 模型记录中解析。只有 `model.input.includes("image")` 才启用图片传输。未知模型 id 和自定义模型 id 一律走保守的非视觉路径，即使发现元数据声称 `vision` 也不例外。
3. Electron 主进程仍然是附件的边界。它会将每个源路径与会话 scratch 根目录、会话绑定的项目根目录或内容寻址的附件根目录进行校验。图片以 `attachments/<sha256>` 形式存储，持久化的 `UiMessage` 只保存引用和元数据。
4. 对于支持视觉的模型，处于 20 MiB 内联上限之内的图片仅以临时 base64 数据的形式跨过 sidecar，并成为 pi-ai 的图片内容块。base64 值永不持久化到 SQLite、JSONL 或渲染器 transcript 状态中。
5. 对于非视觉模型、未知模型，或超过内联上限的图片，prompt 会收到安全的 `@path` 回退形式。在把该回退暴露给模型之前，内容存储中重放的图片会先被复制到会话 scratch 的 `replayed/` 目录。
6. 当有图片被附加时，输入框会显示一行紧凑且可访问的状态信息：它会说明所选模型能否接收视觉输入。模型选择器以及会话/供应商摘要会暴露同一套权威的视觉能力。

## 影响

- GPT/支持视觉的模型可以检查粘贴的图片，而无需模型专属的渲染器实现。
- 纯文本模型和非视觉模型保留既有的文件工具工作流。
- 图片字节会被去重，并且可以在重试、fork 和运行时重建后继续存活，而无需把二进制数据放进 transcript。
- 附件垃圾回收仍是后续的存储任务；引用采用内容寻址，因此可以在不改变消息契约的前提下加入该功能。
- 完整的视觉预览、拖放、图片变换以及供应商专属的图片限制仍不在范围内。20 MiB 内联阈值是应用侧的安全上限；供应商可能施加更严格的限制并返回其常规的供应商错误。

## 被否决的备选方案

- **始终发送 `@path` 文本：** 保留了非视觉行为，但无法满足视觉模型。
- **信任渲染器/供应商的发现标志：** 可能宣称某个运行时适配器无法序列化的能力，并且会让未知模型无法安全分类。
- **在消息中持久化 base64：** 会使重新加载以及 SQLite/JSONL 的增长无上限，并且不必要地跨越了持久化边界。
