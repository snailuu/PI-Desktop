# ADR 0102：发布者自有插件源码，工件存储由 Git 托管

## 背景

当前已发布的插件市场把一切都存放在一个仓库中。`vastsa/pi-desktop-plugins`
在 `plugins/<id>/` 下保存插件源码，在 `packages/*.piplug` 下保存已构建的包，
并保存客户端读取的 `catalog.json`。发布意味着维护者把别人的源码提交进插件市场
仓库，并用一个本地脚本重新生成目录。

这个模型无法支撑第三方发布者：

- 插件源码在插件市场仓库之外没有归属者。发布者无法独立迭代、打标签或做版本管理。
- 插件市场仓库会永久性地堆积二进制包，其 Git 历史就这样意外变成了工件存储。
- 没有任何东西把已发布的包与其生成的源码绑定起来。目录记录的是校验和，而不是仓库、提交或构建者。
- `verified` 是手工编辑的目录字段。拥有提交权限的发布者就可以声称它是 verified。
- `download_url` 会跟随重定向到任意主机。当所有包 URL 都解析到一个已知仓库下时这还可以接受，而一旦包 URL 由发布者提供就不可接受了。

插件中心设计（`vastsa/pi-plugin-center`）解决了所有权这一半问题：插件源码留在
发布者自己的仓库中，平台存储经过权限校验的快照、构建证据、审查报告以及一个签名
目录。它规定使用 S3/R2 加 CDN 作为工件存储。

我们希望获得这套所有权模型，但不想自己运营对象存储。

## 决策

### 1. 发布者的仓库是事实来源

发布者提交一个仓库坐标——规范的 HTTPS 仓库 URL、路径，以及一个能解析为 40 位
十六进制提交的 ref。PI-Desktop 绝不把插件源码复制进任何项目方拥有的仓库。
`pluginId`、`publisherId`、所关联的仓库以及打包后的 `manifest.json` 身份必须一致，
并且一个已发布版本精确固定到一个 `(repository, commit, path)` 三元组。

### 2. 管理与分发是两个独立仓库

`vastsa/pi-plugin-center` 是管理平面：提交、所有权验证、隔离构建、审查、策略门禁，
以及记录已发布内容的注册表。

`vastsa/pi-desktop-plugins` 继续作为分发仓库。它继续从根目录提供
`catalog.json`、从 `packages/` 提供包，其 CNB 副本继续做镜像。没有 S3，没有 R2，
也没有单独运营的 CDN。

- 发布者在自己仓库的某个 release 中构建并附加 `<id>-<version>.piplug`，或者由
  center 的隔离 runner 从固定的提交构建它。
- center 校验字节内容，然后把该包提交到 `pi-desktop-plugins/packages/`，同时提交
  一份重新生成的 `catalog.json`，两者在同一个提交中。
- 包 URL 保持相对路径，因此它们会相对于提供目录的那个主机解析。因此在 GitHub
  与 CNB 镜像之间切换既不会把下载指向另一个供应商，也不会改变正在校验的校验和。

把分发保持在原有位置，意味着默认目录 URL 永不改变，也没有任何已安装的客户端需要
迁移。它还意味着工件字节与描述它们的摘要落在同一个 Git 提交中，这比 release 附件
是更强的记录：改变已发布的字节需要重写历史，而不是重新上传一个文件。剩余风险是
强制推送（force-push），这预期由分发仓库上的分支保护来防止。

被接受的代价是仓库增长。提交进去的二进制文件是永久的——一个未使用的版本可以从
`packages/` 中删除，但它仍留在历史里，因此每次克隆都要为曾经发布过的每个版本付出
代价。

### 3. 目录 schema v2 是客户端契约

`catalog.json` 新增 `schemaVersion: 2`，并按版本记录：源码仓库、ref、提交和路径；
构建者身份；审查决策、风险层级和策略版本；`yanked` 状态；以及可选的分离签名。
客户端继续无差别读取 v1 目录，因此现有插件市场仓库和任何自定义源在迁移期间都能
继续工作。

### 4. 主机限制包可以来自何处

由于包 URL 现在受发布者影响，host-core 对插件市场包强制执行下载主机允许列表：
GitHub 的 release 与 raw 资源主机，以及 CNB 主机。重定向被限制为 HTTPS，并且最终
有效 URL 会重新对照允许列表校验。自定义或企业目录只能从提供其自身目录的主机下载，
除非用户显式配置了额外主机。

### 5. 信任与审查结论由 center 发布，绝不由发布者声称

`trust`、`review.decision`、`review.risk` 和 `policyVersion` 由 center 的策略评估器
写入。发布者提交的元数据无法设置它们。对于任何无法归属于 center 的内容，客户端
一律渲染为 `community`，并且绝不把无法验证的声明渲染为 `verified`。

### 6. 被 yank 的版本不可安装

`yanked: true` 会把该版本从安装与更新选择中移除，但在版本历史中保留其可见性并附带
原因，同时把已安装的副本标记为需要关注。

## 后果

- 第三方发布者可以发布插件，而无需对任何 PI-Desktop 拥有的仓库有写权限，并且可以
  按自己的节奏做版本管理。
- 默认目录 URL 不变，因此无需客户端发版，也无需用户操作就能获取通过 center 发布的
  插件。
- 客户端无需为此决策改动代码：相对包 URL 已经相对于携带它们的目录解析，而下载主机
  允许列表已经覆盖两个分发主机。
- 每个已安装的插件市场插件都可追溯到某个仓库和提交，桌面端可以在安装前展示这一
  来源信息。
- 失去对象存储的代价是失去 WORM 语义和带版本控制的存储桶保留策略。上述 Git 记录
  是防篡改可检测的，而非防篡改的，并且分发仓库会无界增长。两者都是被接受的取舍。
- 在分发仓库同时提供 v1 条目与 center 发布的 v2 条目期间，客户端必须同时容忍两种
  目录 schema。
- 发布者签名密钥仍不在范围内。由 center 签名；发布者持有的密钥留待 ADR 0008 的后续
  阶段。

## 被否决的替代方案

- **把源码保留在插件市场仓库中。** 简单、已经可用，但无法支持不是维护者的发布者。
- **只做索引；从发布者仓库下载。** 这会把 center 完全移出下载路径，但发布者可以从
  已发布版本脚下删除或替换某个 release 附件，而客户端将需要一份无边界的主机允许
  列表。
- **把工件作为分发仓库的 release 发布。** 这样可以让 Git 历史中不含二进制文件，并
  允许修剪旧版本，代价是目录必须声明一个工件基址，而 CNB 镜像必须单独复制 release
  附件，无法随现有的 Git 镜像一并带过去。
- **由 center 从源码构建每个插件，不使用发布者提供的工件。** 可复现性最强，并让
  center 从第一天起就对每个插件的工具链和依赖供应链负责。保留为选择加入的插件的
  runner 路径，而不作为唯一路径。
- **按插件中心文档所述使用 S3/R2 加 CDN。** 提供 WORM、对象锁和缓存控制，代价正是
  本决策所要避免的运维与计费面。
