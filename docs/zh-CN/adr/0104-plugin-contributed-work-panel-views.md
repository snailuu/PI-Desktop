## 背景

在 ADR 0108 移除交互式终端之前，右侧工作面板在渲染器中以硬编码列表的形式暴露了四项能力 —— Review、Terminal、Browser、Files（ADR 0019）：一个 `HEADER_TOOLS` 常量、一个封闭的 `WorkPanelTabKind` 联合类型，以及面板主体中按标签类型进行的四路分支。新增任何界面区域都意味着修改主机核心代码。

插件已经拥有一个成熟且严格受限的 UI 通道，但它只能产出**独立窗口**：`ui.panel` 会打开一个无边框的 `BrowserWindow`，带有沙箱化 preload、按插件持久化的会话分区，以及 `net.domains` 出站允许列表（ADR 0092）。插件无法在主窗口内放置任何内容，因此那些理应紧邻对话的能力 —— Git 历史浏览器、文件管理器、issue 列表 —— 要么变成一个与应用争夺屏幕空间的独立窗口，要么根本不存在。

工作面板是这些界面区域的天然归宿。它已经是"检视并引导工作区"的那一列，已经是会话作用域的（ADR 0028），并且是客户端区域中随流布局的一部分，在可见时还拥有临时预留的原生宽度（ADR 0122）。

## 决策

1. **插件通过 `contributes.views` 声明工作面板界面区域。** 每个条目携带一个 `id`、一个 `title`（纯字符串或 `{ en, "zh-CN" }`）、一个可选的 `icon` token、一个相对于插件的 HTML `entry`，以及一个可选的 `order`。一个插件可以声明多个：Git 插件可以把"Changes"和"History"作为两个独立条目发布。新增的 `ui.view` 权限用于控制这一贡献，与 `ui.panel` 平行；两者相互独立，因此一个插件可以拥有停靠视图而没有独立窗口。

2. **视图作为主进程所拥有的 `WebContentsView` 渲染**，挂载到主窗口，并根据渲染器测量得到的矩形进行定位 —— 这正是预览浏览器自 ADR 0019/0033 以来一直使用的机制。它整体复用插件已有的隔离机制：相同的沙箱化 `plugin-panel` preload、与该插件独立窗口相同的持久化 `persist:pi-plugin-<id>` 分区，以及相同的 `net.domains` 出站过滤。出站策略与分区名被抽到共享函数中，因此停靠与独立两种放置方式不会漂移成不同的安全姿态。

3. **渲染器是可见性的权威。** `WebContentsView` 会合成在渲染器内容之上，因此只要面板不是当前活动标签、面板正在播放动画、分隔条正在被拖动，或有阻塞性浮层处于打开状态，面板就会隐藏所有原生界面区域 —— 浏览器与任何插件视图一视同仁。所有这些情况都由同一个 `panelBlocked` 条件来管控。

4. **嵌入式视图去掉窗口控制栏。** 停靠视图没有可供最小化、最大化或拖动的窗口，因此 preload 跳过 ADR 0092 所定义的三按钮胶囊与 46px 安全区域，转而发布 `--pi-plugin-titlebar-height: 0px` 而非 `46px`。插件作者读取该变量而非硬编码数值，因此同一个 entry 文件在两种放置方式下都能正确布局。`window.pluginBridge` 逐字节完全相同，所以视图与面板可以共享代码。

5. **图标是来自主机核心所拥有的封闭列表的 token**，绝不用插件提供的标记。图标绘制在主机核心 chrome 内、第一方控件旁边；在此处接受 SVG 会构成注入面，并会让插件得以伪装成主机。未知 token 不是错误 —— 它会降级为字母图块 —— 因此针对更新主机编写的插件在较旧主机上仍能正确列出。

6. **视图列表按激活作用域过滤。** 这一点有意与 `pluginThemes` 不同，后者*不*按作用域过滤，因为所选主题是一个全局的应用设置。视图是插件在项目内所做的事情，因此项目作用域的插件不得在另一个项目中提供其视图。打开视图时会重新检查权限、作用域与 entry 是否存在；渲染器从不是"插件可以显示什么"的权威。

7. **视图被缓存、有边界，并绑定到插件的生命周期。** 视图在标签切换后仍然保留，以便插件保持其滚动位置和页面内状态，最多同时存在四个存活视图，淘汰最近最少展示的视图，且绝不淘汰当前屏幕上那一个。禁用、卸载、重新加载和崩溃都会销毁该插件的视图；标签可能比页面存活更久，因此渲染器在生命周期事件发生时重新打开，而不是留下一个永久空白的窗格。

## 后果

- 工作面板从固定集合变为扩展点。第三方插件通过第一方代码在 ADR 0103 的迁移落地后将要使用的同一条路径抵达它，这正是让那次迁移成为对插件 API 是否充分的真正检验的原因。
- 无论放置方式如何，插件的存储都是一回事，因为视图与该插件的独立窗口共享同一个分区。因此打开视图会继承面板窗口已经拥有的任何会话状态。
- `windowForSender` 必须直接扫描窗口，而不能先解析插件 id：停靠视图现在也会解析到一个插件 id，若让窗口控制经由该路径，停靠视图就可能关闭同一插件的另一个窗口。这一点由测试断言，而非留给代码评审。
- ADR 0019 为浏览器所接受的 z-order 注意事项现在适用于每个插件视图。顶部居中的 toast 可能与视图的角落重叠；阻塞性浮层则会完全遮住它。
- 四个存活的 `WebContentsView` 最坏情况下意味着多出四个渲染器进程。这一上限是针对"每次切换标签都销毁并重新加载插件页面"的有意取舍。

## 已考虑的替代方案

### 在主机渲染器内使用 `<iframe>`

已拒绝。它能正确处理 z-order，也不需要同步边界，但 Electron 无法为 iframe 提供独立的会话分区，因此插件页面会与主机渲染器共享进程和存储。这比插件窗口已有的边界严格更弱，而且无法对其执行 `net.domains` 允许列表。与现有面板窗口保持隔离对等才是关键。

### 由主机渲染插件提供的 React 组件

直接拒绝。这会把第三方代码放进主机渲染器，使其能访问应用自身的状态和 IPC 桥，为了渲染上的便利而丢弃整个插件信任边界。

### 复用 `ui.panel`，由主机决定在哪里显示

已拒绝。panel 是每个插件一个界面区域，具有窗口的尺寸和标题；view 是多个界面区域之一，由面板列来定尺寸，并且需要自己的菜单标签、图标和顺序。把两者塞进同一个字段会让双方都变差，并且让插件无法既提供停靠视图*又*提供独立窗口。

### 两者兼有，通过 `isolation: "process" | "inline"` 清单字段选择

本次变更中已拒绝。它会使渲染与安全路径翻倍，而所换取的性能收益尚未被测量，并且更弱的模式会仅仅因为它更容易上手编写而变成默认选项。
