# ADR 0109：使用操作系统关联的应用程序打开文件条目

## 上下文

内置的 `pi.files` 视图可以在其隔离的查看器中检查文本，但图像、文档、压缩包及其他文件更适合由操作系统关联的应用程序处理。现有的 `shell.openExternal` API 有意只接受 Web 和邮件 URL，因此若将工作区路径转换为 `file:` URL，要么会削弱该边界，要么会给插件一个无作用域限制的文件打开器。

## 决策

1. 新增 `pi.fs.openDefault(pathFromRoot)` 以及对应的面板桥接通道
   `fs.openDefault`。
2. 该 API 由现有的 `fs.read` 权限覆盖。主机通过完整的读取门控来解析相对于根目录的路径：工作区/用户选定的根目录、真实路径包含检查、受保护路径、拒绝列表，以及已声明的作用域或用户同意。它仅接受已存在的常规文件。
3. 通过门控后，Electron 主进程调用 `shell.openPath`，由操作系统选择文件关联。插件永远不会收到绝对路径，也无法选择可执行程序或命令行。
4. 内置的 Files 视图仅在其选中的文件查看器中暴露该操作，包括二进制和图像文件。成功与失败都会按插件 id 和相对于根目录的路径进行审计。
5. 这是一次增量式的插件 API 变更；桌面端 IPC 和主机协议版本不变。现有的 `shell.openExternal` URL 限制保持不变。

## 后果

- 文件可以交接应用内文本查看器无法渲染的内容。
- 默认应用程序可能会按其自身行为复制、转换或同步文件；用户须从查看器中明确发起该交接。
- 拥有 `fs.read` 的插件仍然无法通过此 API 打开凭据、仓库内部文件、受保护的应用数据、任意绝对路径或目录。
- 操作系统交接失败会以 `OPEN_FAILED` 报告给插件，并通过 Files 视图的错误提示浮层可见。

## 考虑过的替代方案

### 复用 `shell.openExternal` 并传入 `file:` URL

已拒绝：该 API 用于外部链接，会模糊 URL 出口与本地文件访问之间的界限。这也会使文件作用域难以一致地强制执行。

### 新增一个私有的内置插件 IPC 通道

已拒绝：Files 有意作为公共插件 API 的消费者。私有桥接会重新引入 ADR 0105 已移除的信任边界例外。

### 在 `fs.read` 之外新增一个独立权限

针对此操作已拒绝：主机不暴露任意打开器。该路径必须已经是插件已声明作用域内可读的文件，并且 UI 操作不允许插件选择可执行程序或 URL。该操作仍会被审计，以便后续策略变更时有明确的边界可供修订。
