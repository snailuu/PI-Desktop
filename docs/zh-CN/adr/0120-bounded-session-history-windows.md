# ADR 0120：有界会话历史窗口

## 上下文

此前打开会话时会读取其完整的 JSONL 记录，投影每一条消息，并将完整结果经由主机核心、Electron 和渲染器发送。因此，一个大型的粘贴值或工具产生的值就可能造成 50 MB 的记录分配，并在打开长会话时阻塞桌面端。挂载时虚拟化并不能解决该问题，因为完整载荷已经跨过了进程边界。

## 决策

1. 面向渲染器的 `session.get` 支持通过 `messageBefore`、`messageLimit` 和 `contentLimit` 进行增量读取窗口。宿主返回 `messageStart` 和 `hasMoreBefore`，使渲染器可以在保留最新视图的同时向更早的消息分页。
2. 主机核心使用带缓冲的顺序解析器读取 JSONL，并只投影所请求的页面。`contentLimit` 只截断派生的显示投影，并带有明确标记；磁盘上无损的记录以及未设上限的 sidecar/模型路径仍为权威来源。
3. 桌面端打开会话时使用最新的 100 条消息和每条消息 64 KiB 的显示预算。滚动到接近顶部时会获取更早的页面，并保持视口的滚动位置。有意进行的全历史重写会先完整重新水合记录再替换它，因此渲染器的部分窗口不会删除更早的消息。
4. 非渲染器调用方仍可使用未设上限的默认行为，因此模型重建和持久化语义不依赖于 UI 分页。

## 考虑的替代方案

- **仅虚拟化消息列表：** 已拒绝，因为昂贵的完整解析和 IPC 载荷仍会在渲染之前发生。
- **在记录中仅存储预览：** 已拒绝，因为这会丢失用户数据并改变模型上下文语义。
- **使用数据库载荷表进行分页：** 目前拒绝；JSONL 记录仍是无损来源，而流式窗口避免了 schema 迁移，同时修复了导致卡顿的边界问题。

## 后果

- 会话激活时，渲染器内存和 IPC 工作量有界，且与可见历史总量无关，唯一例外是为定位所请求页面而需要的顺序扫描。
- 更早的历史可按需获取，仅用于显示的截断对用户清晰可见，而完整内容仍对代理可用。
- 全历史编辑、删除、修订切换和中止操作在变更前可能会执行有意的不设上限读取；这会保留记录数据，而不是让部分 UI 窗口覆盖更早的消息。
