# ADR 0128：为瞬态供应商故障共享一份有界预算

> **翻译说明：** 本页是与 [英文源决策](/adr/0128-bounded-transient-provider-retry) 一一对应的机器辅助翻译。代码、协议字段和标识符保持原文；如翻译与英文源事实有歧义，以英文版本为准。

## 上下文

网关上游故障在 OpenAI 兼容端点上很常见。一个返回
`OpenAI API error (502): {"type":"api_error","message":"Upstream API
request failed."}` 的中继报告的是上游的瞬时中断，而不是请求被拒绝：同样的
提示词通常在下一次尝试时就会成功。

ADR 0091 为 HTTP 429 提供了共享的五次重试预算，但有意把其他所有瞬态故障留在
更早的拆分策略上：请求建立阶段一次重试，流中途一次重放，各自受自己的布尔标志
保护。由此产生了两个缺口。第一，在响应头到达之前出现的 502 消耗掉了那唯一一次
建立阶段重试，于是第二次 502 就变成终态错误卡片，即使第三次尝试很可能已经成功。
第二，流阶段完全排除了 `PROVIDER_ERROR`，因此流中途发生的网关故障根本不会被重放。
内置子代理更严格：其判定要求 `phase === "request"`，所以委托在第一个流中途瞬态
错误上就失败了。三个供应商入口（主会话、子代理、输入框增强）已经漂移成了三套
不同的策略。

非 429 的退避同样忽略了 `Retry-After`。那些在 502/503 时携带显式
`Retry-After` 的网关，无论服务器要求什么，都会被按固定的 750 毫秒流中途计时器
或 500 毫秒建立阶段计时器重试。

## 决策

1. 非 429 的瞬态供应商故障共享一份有界的逻辑回合预算：在初次尝试之后重试四次，
   即总共五次供应商尝试。该预算由请求建立与流传输共享，因此跨阶段转移的故障
   既不能重置它，也不能使其倍增。
2. 该预算恰好接纳 `NETWORK_ERROR`、`TIMEOUT`、`STREAM_FAILED` 和
   `PROVIDER_ERROR`。`PROVIDER_ERROR` 现在在流阶段和建立阶段都会被接纳。其他
   所有分类，包括来自畸形 400/422 请求的不可重试 `PROVIDER_ERROR`，都保持
   终态。
3. 重试延迟优先遵循服务器。`retry-after-ms`、`retry-after` 秒数，然后是
   `retry-after` HTTP 日期，均优先于客户端退避；对于非 429 路径，上限为
   8 秒。对于任何可携带可用延迟的状态码（429、408、409 和 5xx），都会保留
   捕获的响应头，而不只是 429。没有可用响应头时，等待是简单的倍增序列：
   1、2、4，然后 8 秒，在两个阶段中完全一致且是确定性的（无抖动），因为它
   调节的是单个失败请求，而不是同步的速率限制爆发。
4. 主会话、内置子代理和一次性输入框增强使用相同的错误码、相同的预算规模和
   相同的延迟优先级。
5. 重试保持静默且可中止，429 保留其来自 ADR 0091 的独立的五次重试预算。两个
   预算互不取用。
6. 预算耗尽时发出一个终态助手错误和一个生命周期错误；对于持续的非 429 瞬态
   故障，`retryAttempt: 4`。
7. 只重放失败的那个请求。会话、转录和工具状态不受影响：失败的助手会离开下一次
   模型上下文，其可见消息 id 被复用，因此重试永远不会重启回合或重新运行已完成的
   工具调用。

## 后果

- 短暂的上游 502/503/504 爆发无需错误卡片即可恢复，无论它发生在响应头之前还是
  流中途。
- 持续的上游中断保持有界且可见：五次尝试、最多四次退避共 15 秒、单次等待上限
  8 秒。
- 终态非 429 错误之前的最坏延迟会增长，上界为四次等待（15 秒退避）而非一次。
- 自行声明节奏的网关得到尊重，而畸形或过大的响应头值无法卡住回合。
- 三个供应商入口不再漂移成不同的瞬态策略。

## 备选方案

- 改为提高 pi-ai 的 `maxRetries`。拒绝，理由已在 ADR 0091 中记录：嵌套包装层会让
  尝试次数倍增，使预算依赖阶段，并重新引入不可中止的 SDK sleep。
- 将非 429 瞬态故障并入 429 预算。拒绝：速率限制和网关中断需要不同的延迟量级，
  共享一个计数器会让 502 爆发消耗掉速率限制预算。
- 对每个可重试分类都重试三次。拒绝：`EMPTY_MODEL_RESPONSE` 和上下文故障有各自的
  恢复路径，重新发送同一请求无法修复它们。
