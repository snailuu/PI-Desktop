# ADR 0129：子代理空闲看门狗约束的是静默，而非缓慢

## 上下文

ADR 0119 用空闲看门狗取代了委派回合上限，该看门狗的计时器由一份五种事件类型的允许列表重新计时。问题出在这份列表，而不是策略本身：它按事件的*种类*判定存活，因此任何不在此列表中的 `AgentEvent` 变体——无论是现有的还是未来的——都会被静默丢弃，而阅读代码也无法回答看门狗本应回答的问题。一个流式输出缓慢的委派是否仍然存活，取决于恰好被列入列表的类型，是偶然结果，而不是一项明确的契约。

会话遥测还表明，600 秒这个默认值是在没有参照其所度量的对象的情况下选定的。由于计时器会被流式输出重新计时，并在工具执行期间暂停，它实际约束的唯一区间，是委派上一次流式输出的 token 与其下一次响应之间的等待。在本项目中，该等待的度量值为 p50 5.6 秒、p90 13.4 秒、p99 55 秒、p99.9 174 秒——比 600 秒低一个数量级。与此同时，600 秒恰好等于 `TaskWait` 的默认值，因此一个挂起的委派无法在单次等待内结算，而父级会把一次普通的未完成等待读取为委派失败。

另外，内置代理完全没有回合兜底，因此一个循环而无法收敛的委派会一路运行到 6 小时的时长上限。

## 决策

1. 每个 `AgentEvent` 都会重新计时空闲计时器，包括以 `message_update` 形式到达的单个流式 token。看门狗只在完全无响应时触发，除此之外不因任何原因触发。`tool_execution_start` 与其配对的 `tool_execution_end` 之间的暂停保持不变，时长计时器贯穿工具执行也保持不变。
2. 默认空闲超时为 300 秒，依据是实测的 174 秒 p99.9 token 前等待，再为委派自身供应商的重试退避留出余量，该退避按设计是静默的。它必须低于 600 秒的 `TaskWait` 默认值，以便真正卡住的委派能在单次等待内以 `timed_out` 结算。21,600 秒的时长上限与 10–21,600 的覆盖范围界定保持不变。
3. `TaskWait` 过期时报告 "Still running after Ns"，并说明这不是失败，未完成的委派会继续工作。
4. 内置代理按其职责设有回合兜底：`explorer` 60、`code-reviewer` 50、`test-runner` 40、`fixer` 80。无法收敛的委派会以 `truncated` 结束并返回其部分报告，而不是运行到时长上限。

## 考虑过的替代方案

- **保留事件允许列表，仅降低默认值：** 否决，因为它让存活判定依赖于一份枚举，每当 `AgentEvent` 新增变体都必须重新检视，并且使预期契约始终未被说明。
- **在供应商重试退避期间发出合成活动：** 暂予否决。对于运行时自身选择等待的那一个区间而言，这是更有原则的修复，但它会让看门狗对某个失败后永久退避的供应商视而不见。把窗口设定在重试范围之上，可以让存活判定保持单一事实来源。若重试预算增大，可重新考虑。
- **把空闲默认值提升到 900 秒并延长 `TaskWait`：** 否决，因为它颠倒了真正重要的关系——空闲窗口必须短于一次等待，否则卡住就无法在单次等待内浮现。
- **让内置代理保持不限回合：** 否决，因为时长上限是 6 小时的兜底，而非收敛信号；循环的委派应当在几分钟内返回其部分工作。

## 后果

- 只要委派持续产出输出，就永远不会因空闲而被终止，无论其回合有多慢。只有静默才会使其过期，而且原因在代码中是清晰可读的。
- 两类此前尚可幸存的场景现在会在 300 秒而不是 600 秒过期：极端的供应商延迟离群值，以及一长串速率限制退避。两者都会返回 `timed_out` 并附带最新的部分报告，而不是被丢弃。
- 挂起的委派会在单次 `TaskWait` 内浮现，而不再让父级被占用一整个窗口乃至更久。
- 新增 `AgentEvent` 变体不再需要改动看门狗。
