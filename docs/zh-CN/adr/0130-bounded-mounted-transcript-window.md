# ADR 0130：有界挂载的对话记录窗口

## 上下文

ADR 0120 对跨越 IPC 边界的对话记录负载施加了上限，ADR 0127 / D258 则对在 JSONL 文件中定位某一页的成本施加了上限。两者针对的都是会话的*激活*过程。二者都没有约束渲染器在此之后持续挂载的内容。

渲染器会把它已分页载入的每一行历史都挂载，并在会话的整个生命周期内保持挂载。因此，向上滚动浏览一段很长的对话会不断累积且没有任何上限：

- 每一行的 React 元素树，
- 每个已稳定块的解析后 Markdown AST，
- 每段代码围栏的 Shiki `LineCache` token 数组，
- 以及 DOM 节点本身。

`.message-row` 和 `.tool-activity-group` 已经带有 `content-visibility: auto`，它会跳过远离视口的行的布局与绘制。这是一种 CPU 优化，而明确不是内存优化：被保留下来的 JavaScript 与 DOM 依然存活。在一台低内存 Windows 机器上——有报告称随着会话增长，聊天区域逐渐变得越来越不响应——被保留的内存及其背后的 GC 压力才是真正的约束。

另一项成本是逐帧的。当 props 数组不是引用相等时，`TranscriptHistory` 的 memo 比较器会遍历每一个已挂载的条目、part 和活动项，而这个过程会在每个流式 token 上运行。

## 决策

1. 已挂载的历史是覆盖已加载历史的**尾部窗口**，而非全部。`reduceTranscriptWindow` 为单次渲染解析出切片：会话切换后的首次提交使用 `TRANSCRIPT_INITIAL_MOUNT`（15）行，稳态下使用 `TRANSCRIPT_WINDOW_MIN`（60）。
2. 到达顶部时会**分两阶段升级**。在窗口仍处于部分状态时，`growTranscriptWindow` 增加 `TRANSCRIPT_WINDOW_STEP`（40）行；只有当窗口覆盖了全部已加载历史之后，记录视图才会调用 `loadOlder` 并拉取更早的一页。挂载已经加载的内容严格比一次 IPC 往返更便宜，因此它先行。
3. 窗口增长与拉取页面使用**同一个绘制前滚动锚点**。两者都会在阅读位置上方增加高度，因此 `prependHeightRef` 对两者都进行捕获，并在同一个布局副作用中修正。
4. 窗口**按会话重置**，并被钳制在已加载历史的范围内，因此从上一个会话继承而来的、已经增长的预算不会在某一帧造成过度挂载。
5. 水合占位元素始终**仅限于首次提交**。它的存在是为了让有界底部可达；如果把它保留在稳态窗口下，就会在用户与增长触发器之间留下一段空白视口。
6. 对话迷你地图的**消息短横线**基于**已挂载条目**（`transcriptEntryMessages`）构建。它通过在滚动容器内查找该标记的 `data-minimap-id` 节点来解析点击，因此为被扣留的行渲染消息标记会得到指向虚无的短横线。
6a. **由 D269 修订。** 被扣留的历史会被显式表示，而不是被默默丢弃：当已加载的行位于窗口之上（`hiddenAbove > 0`）或宿主报告存在更早的一页（`hasMoreBefore`）时，轨道保持挂载，并显示一个点状的更早历史延续标记，即使已挂载的尾部少于两个消息标记，或本身不超出一个视口。该延续标记运行与第 2 条相同的两阶段升级，因此它始终可操作；一旦不再有更早的历史，D108 的“两个标记加溢出”规则便恢复生效。
6b. **由 D269 修订。** 升级的驱动既包括记录视图顶部加载边界的可见性，也包括近顶部滚动检查，两者使用同一个共享阈值。一页未填满的尾部、一页其行全部落在已挂载窗口之外的已拉取页面，以及窗口切换，都可能使 `scrollTop` 保持不变；在缺少被观测的边界时，这些状态会阻塞向上浏览并让轮廓保持隐藏。
7. 条目投影数组以 `entries` 为依赖做了 memo 化，因此一次没有改变任何消息的重渲染会把一个引用相等的数组交给 `TranscriptHistory`，其比较器便可依据标识直接退出，而不必深度遍历已挂载的行。

不涉及任何 IPC、存储、宿主协议或分页改动。`SESSION_TRANSCRIPT_PAGE_SIZE` 与 `session.get` 的窗口契约均未改动。

## 考虑过的替代方案

- **仅依赖 `content-visibility`：** 拒绝。它已经就位，而且正是它让*无界*场景尚且可用，但它保留了每一行的 React 树、Markdown AST 和 token 数组。它无法约束这份低内存报告所关注的那类资源。
- **采用带测量行偏移的完全虚拟化：** 目前拒绝。记录行的行高高度可变且依赖内容，并会在挂载后发生变化（流式、展开切换、懒加载 Mermaid），因此基于测量偏移的虚拟化器需要为这一切准备高度缓存与失效机制。尾部窗口以少得多的活动部件达到同样的内存上限，而现有的固定跟随与前置锚点逻辑保持不变、继续工作。
- **按与视口的距离双向卸载：** 拒绝。记录视图是从底部读取、并在底部流式输出的；扣留视口*下方*的行只会与固定跟随相互冲突，而没有任何收益。
- **改为限制已加载历史，从 store 中丢弃更早的页面：** 拒绝。这会让分页变为非单调，并重新拉取用户刚刚滚动过去的内容；而且 store 中的记录还会被结果卡片和全历史重写路径读取。
- **通过让投影引用稳定来降低逐帧比较器成本：** 仅以其廉价形式（对数组做 memo 化）保留。跨重建调和每回合的对象标识被拒绝，因为这属于额外复杂度，而有界窗口已使其不再必要——比较器现在最多遍历窗口，而不是整个历史。

## 后果

- 一段对话记录所占用的渲染器保留内存由窗口而非用户已回滚的深度决定，流式期间的逐帧调和同样被限定在窗口内。
- 在长会话中向上浏览时，在分页恢复之前，每个增长步骤会先消耗一帧。每一步都是挂载已经加载的行，因此不会增加 IPC。
- 浏览器原生的页面内查找只能到达已挂载的行。这确实是对一项附带能力范围的收窄；应用内针对完整对话记录的搜索不受影响，因为它不依赖已挂载的 DOM。
- 新挂载的行在真实尺寸已知之前，会短暂使用 `contain-intrinsic-size` 的兜底高度，因此滚动条滑块会随着它们进入视口而稳定下来。这是既有的 `content-visibility` 行为，窗口化并未改变其性质。
