# ADR 0132：跨显示器窗口移动归属于用户

## 背景

ADR 0122 为停靠的工作面板保留了一个目标状态、显示器感知的原生预留。主进程根据记住的*基础边界*——即不含预留的窗口矩形——来规划预留，并将后续的原生增量与它实际应用的最后一个矩形进行对账。

该对账把两种截然不同的情况压缩进一个 `displayChanged` 布尔值。当窗口最终落在另一台显示器上时，记住的基础边界被原样复用，然后被钳制到新显示器的工作区内。当操作系统只是重新适配了我们请求的边界时，这是正确的：用户的意图在受限显示器上得以保留，并在宽敞显示器上被恢复。但当用户把窗口拖到那里时，这就是错误的，因为前一台显示器的坐标不再是意图。

更糟的是，对账被绑定到每一个原生 `move` 事件上，因此在拖拽仍在进行时它就会运行。issue #18 中报告了此问题，并且从 0.10.0 起的每个版本上都可复现：把窗口拖到第二台显示器时，它会在指针释放时跳动，因为延迟的 `setBounds` 是根据原显示器的基础边界规划的，结果落在了目标显示器被钳制后的边缘。窗口的 y 坐标也来自旧显示器。同样的错误归属随后渗入 `window-state.json`，因此重新启动时窗口在用户已离开的那台显示器上重新打开。

## 决策

1. 将 `displayChanged` 布尔值替换为显式的 `DisplayTransition`，取值为 `none`、`os-adjusted` 或 `user-moved`。
2. `os-adjusted` 保持 ADR 0122 的行为不变：记住的基础边界在操作系统重新适配或显示器拓扑变化后仍然保留。
3. `user-moved` 从窗口当前位置推导出新的基础边界，因此落点位置成为意图。只有原点会被归一化到目标显示器的工作区内；即使目标工作区更小，尺寸也会保留，因为按 ADR 0122，基础边界是可恢复的意图，而此处的缩小会被永久持久化。
4. 根据其前面是否有一段未被归属的原生 `move` 流来对该转换进行分类。拖拽是唯一会跟随这种流的跨显示器转换。该标记是一个标志，而非截止期限，因此归属绝不取决于主进程用了多长时间才完成分类，并且它能在最大化或全屏窗口的延迟几何计算中存活。
5. 绝不在拖拽过程中重新规划边界。`move` 处理器只标记用户移动窗口，并将显示器对账推迟到移动流安静下来之后。
6. 对 `none` 和 `user-moved` 都持久化基础边界，并在 `user-moved` 时推进记住的显示器键，这样重新启动时能恢复用户实际让窗口停留在的那台显示器。`os-adjusted` 仍然拒绝持久化。持久化路径以同样方式归一化被拖入的基础边界，因为最大化或全屏窗口会延迟预留几何计算，使这成为该拖拽的唯一消费者。
7. 在截止期限到期时废弃未被消费的标记。该截止期限限定了在没有消费者运行时标记能滞留多久；它绝不决定归属。
8. 强制的边界恢复（Stage Manager 路径）会清除待处理的用户移动归属，因为它不是用户意图。

## 后果

- 在显示器之间拖拽窗口会保持其被放置的位置，指针释放时不会跳动。
- 重新启动会在上次使用的显示器上重新打开窗口。
- 对于操作系统主导的调整，ADR 0122 的受限显示器预留行为被原样保留，包括恢复到宽敞显示器的路径。
- 显示器拓扑事件会在对账之前清除待处理的标记，因此紧接拖拽之后新增、移除或缩放显示器仍会被归类为操作系统主导。
- 被放置到工作区容纳不下它的显示器上的窗口会保留其尺寸，并被固定到工作区的左上角。`planWorkPanelReservation` 仍会对其增加的宽度设上限，因此是预留缩小而不是窗口缩小。
- 无 IPC、存储或宿主协议变更。`window/setWorkPanelReservation` 保持其请求/响应形态。

## 备选方案

### 将记住的基础边界钳制到新显示器中

已拒绝。它让窗口留在目标显示器上，但丢弃了落点位置，而落点位置正是所报告的症状，而非该症状的修复方案。

### 在显示器变化时完全跳过预留规划

已拒绝。那样预留就会按前一台显示器的工作区来定尺寸，于是更窄的目标显示器会让窗口比其工作区还宽。

### 从指针状态而非移动流来检测拖拽

暂不采纳。Electron 没有为原生窗口移动暴露拖拽开始/拖拽结束的事件对，而在拖拽期间轮询指针的成本比它所替代的待处理移动标记更高。

### 用时间截止期限来归属拖拽

已拒绝。截止期限会让正确性依赖于主进程的调度：一个繁忙的主进程，或者一个把几何计算推迟到截止期限之后的最大化窗口，都会静默回落到有缺陷的 os-adjusted 路径。
