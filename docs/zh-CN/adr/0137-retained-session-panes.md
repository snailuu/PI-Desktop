# ADR 0137：保留的会话窗格

## 背景

D162 已经避免了最糟糕的会话切换工件：它让最后一次稳定下来的对话记录保持挂载，而不是把它拆解成骨架屏。但切换时仍会闪烁，因为让*某个*对话记录保持挂载，并不等于让*目的地*的对话记录保持挂载。

store 为活动会话只持有一个 `messages: UiMessage[]`，切换时会整体替换该数组。单个 `ChatTranscript` 实例服务于所有会话，因此在 `sessionId` 变化时，它必须手动重置滚动位置、已挂载行窗口和水合状态，而且由于行键以消息为作用域，每一行都会被重新挂载。用户片刻之前才读过的对话记录被重新解析 Markdown，并被 Shiki 重新分词。

由此产生三项可见代价：

- 保留的帧被**变暗**（`opacity: .82`、`pointer-events: none`），并处于一条细进度条之下。在热重新访问时，目的地内容已经在渲染器内存中，因此变暗只是为一段并不需要发生的工作播放的等待动画。
- **滚动位置并不属于窗格**。一个滚动容器无法同时持有两个阅读位置，因此当用户返回到一个他曾向上滚动的会话时，会从底部重新开始；而为了避免继承*上一个*会话的偏移量，这个重置还必须显式执行。
- ADR 0130 第 5 条中的**两阶段渐进式水合**在每次切换时都会运行：在一个 `100vh` 占位器之后先挂载尾部 15 行渲染一帧，然后在 rAF 中展开并重新锚定。它之所以存在，仅仅是因为组件实例是共享的，而它恰恰是最容易产生它本就想要防止的那种跳动的机制。

## 决策

1. `ChatSurface` 按会话 id 键控，为每个**保留的会话 id 挂载一个 `SessionPane`**。窗格在其整个生命周期内拥有自己的对话记录 DOM、滚动位置和已挂载行窗口，因此切换只是可见性互换，而不是重建。
2. 保留策略是**容量上限为 3 个窗格的有界 LRU**：可见窗格加上最近访问的两个窗格。`retainedSessionIds` 在 store 中保存该顺序，淘汰时卸载最旧的窗格。
3. 非活动窗格保持挂载，通过 `visibility: hidden` + `content-visibility: hidden`、`aria-hidden` 隐藏，且不可交互。它明确**不是** `display: none`：后者会销毁布局盒，而布局盒正是持有 `scrollTop` 的东西，所以用 display 隐藏会重置所有保留的阅读位置，使整个决策失效。
4. `messages` 仍然是 **store 活动会话的实时投影**。store 增加了一个有界的按会话快照记录 `retainedTranscripts`。当某窗格所属会话就是 store 活动会话时，该窗格渲染 `messages`，否则渲染自己的快照，因此任何窗格都不会渲染另一个会话的行。
5. **热切换**——目的地已经拥有保留的窗格——会立即用该窗格保留的内容将其显示出来。第一帧就已经是正确的：没有变暗、没有骨架屏、没有重新挂载。随后重新校验得到的对话记录落入同一窗格，且没有可见变化。如果目的地仍在运行，或者仍持有持久化页面尚未追上的已完成回复，该重新校验会按时间顺序把有界的持久化页面缝接到实时快照上（较早的实时行在页面之前，进行中的或尚未刷出的尾部在其之后），这样 D261 的尾部已挂载窗口仍能显示最新回合（D317、D324）。只有当该页面已包含所有实时行之后，才会清除实时来源标记。
6. **冷切换**——没有保留的窗格——会让当前可见窗格在目的地提交之前继续显示自己的会话。只有细进度条标记这段等待。不透明度变暗被完全移除。
7. **滚动位置的保留是按窗格进行的**。窗格再次可见时恢复自己的位置：仍贴底的窗格重新锚定到底部，用户曾向上滚动的窗格则回到那个偏移量。会话的首次激活仍然停在最新回合处。
8. **首次提交是按窗格且局部的**。因为组件实例属于某一个会话，“此窗格的首次提交”就是普通的挂载状态；跨会话的水合占位器、其 rAF 展开以及重新锚定都被删除。ADR 0130 的尾部窗口、两阶段升级和前插锚定在窗格内部保持不变。
9. **输入框为整个聊天表面挂载一次**，而不是每个分支各挂载一次——它本就带有按会话的草稿缓存。当可见窗格还不是 store 活动会话时，它保持不可交互，因此提示不会被发送到正在离开的会话。

不涉及 IPC、存储、宿主协议或分页变更。对话记录读取、最新优先的导航代次以及 D162 的五快照对话记录缓存均未改动；窗格是渲染器侧的展示层约束，而不是第二个缓存。

## 后果

- 保留的渲染器内存最多增加两个额外挂载的对话记录，且每一个本身都受 ADR 0130 的窗口约束。上限是窗格预算乘以窗口，而不是访问过的会话数量。
- 在预算内的重新访问不产生 Markdown 解析、不产生 Shiki 分词、也不产生滚动校正——用户离开时的帧就是他们回来时的帧。
- 已删除：`session-switching` 不透明度变暗、会话加载骨架屏路径、`ChatTranscript` 内部的跨会话滚动/窗口/水合重置、`100vh` 水合占位器，以及按分支的输入框挂载。
- 调用方必须保持四条不变量：
  - **跨会话事件不得写入可见投影。** 后台的消息、工具和完成事件只更新其所属会话的快照；从非 store 活动会话写入 `messages` 会把另一个会话的行绘制到可见窗格中。这与 D142 为工作面板上下文划定的边界相同。
  - **删除会话必须释放其窗格。** 移除会话会删除其 `retainedTranscripts` 条目和 `retainedSessionIds` 槽位，因此没有窗格会比其会话存活更久，也不会持有已删除历史的快照。
  - **在没有活动会话的情况下离开聊天必须丢弃所有窗格。** 切换或清除项目会使保留的会话变得不可达。由于可见窗格是保留顺序的头部，被遗留的窗格会把上一个项目的对话留在屏幕上，并抑制空状态。
  - **隐藏的窗格不执行任何读取工作。** 跟随滚动、历史分页和行位置测量都依赖已渲染的滚动容器；隐藏窗格的滚动容器报告 `scrollTop === 0`，这会被解读为“在顶部”，并会为一个没人在看的会话分页历史。隐藏窗格只保留其 DOM 和偏移量，其他什么都不做。
- 按会话的滚动位置保留**取代**了旧的规则，即激活会重置继承的手动滚动状态——对重新访问而言：重新访问的窗格理应回到用户离开的位置。首次激活保持不变，仍停在最新回合处，且任何窗格都不得显示另一个会话的偏移量。
- 被淘汰的会话表现得像冷打开。这是有意为之，且必须与首次访问无法区分，而不能暴露错误或空帧。

## 考虑过的替代方案

- **用按会话的消息映射替换 `messages`：** 被否决。它只是把同样的整体替换下移了一层——单个对话记录实例仍然一次只读取一个条目，因此行重新挂载、Markdown 重建和共享滚动容器都依然存在。闪烁是组件标识问题，而不是 store 形状问题。
- **深度相等地复用缓存数组：** 被否决。让重新校验得到的读取与缓存数组引用相等只能抑制一次重渲染，却仍让目的地与正在离开的会话共享同一个实例，所以切换后的第一帧仍然是从零构建的。它还要在每次重新校验时对对话记录做一次深度遍历，为的是省下窗格本就在结构上已经省掉的工作。
- **保留变暗，仅在缓存为热时跳过它：** 被否决。变暗从来都不是热切换的可用性提示；一个正确的目的地帧才是。把它保留为条件逻辑会留下两种切换外观需要推敲、两种状态需要测试，而所等待的那段延时其实已被保留的窗格消除。对于冷切换，细进度条已经足够。
- **保留每个访问过的会话的窗格：** 被否决。无上限的窗格会重新引入 ADR 0130 所移除的那种无上限保留，而且是在一台报告过聊天区域性能退化的低内存机器上。三个窗格覆盖了观察到的“切换后返回”模式；第四个就是冷打开。
