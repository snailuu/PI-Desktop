## 上下文

ADR 0062 与 ADR 0089 所构建的委派机制只有一个集成点：父代理。委派代理在生成时收到
一份 `task` 简报，独自运行，并返回一份限制在 12k 字符以内的报告。并发运行的委派代理
彼此不可见。它们唯一的共享物是互斥——sidecar 中的 `PathMutex` 与主机核心的每会话仅
一个进行中变更规则——而两者都是没有载荷的锁。

对于 `Task` 描述所推荐的扇出模式（在一条 assistant 消息中，为每个独立方向分配一个
委派代理），这种隔离是正确的：父代理要求的是彼此独立的答案，并且也确实得到了它们。
一旦这些方向实际上并不独立——而父代理在撰写简报时未必总能知道这一点——它就不再
正确：

- 两个具备写能力的委派代理在运行途中发现它们需要同一个文件。路径锁将写入串行化，
  因此二者不会互相破坏，但第二个的编辑建立在其读取的、早于第一个变更的版本之上。
  锁防止的是撕裂写，而非过时前提。
- 一个委派代理证伪了所有简报都赖以撰写的某个假设。它无从说明这一点。它只能把更正
  写进报告，父代理在 `TaskWait` 之后才读到，而那时其他委派代理已经把各自的回合耗费
  在了错误的前提上。
- 一个委派代理已经找到了另一个代理即将花费十五次工具调用去搜索的事实。两次搜索都在
  各自独立的上下文中全额付费，而在报告落地之前，这种重复是看不见的。

把这些经由父代理中转行不通。委派代理运行期间，父代理被阻塞在 `TaskWait` 中；`task`
是一次性写入的，因此正在运行中的简报无法被更正；而新增一个由父代理中介的中继，
意味着每一条协调备注都会进入父代理的上下文——而这正是委派机制存在的目的所在，
即避免这种开销。

## 决策

新增一个**会话作用域的对等邮箱**和三个仅限委派代理的工具，按定义可选启用。

1. `SubagentMailbox` 由会话运行时持有，每个会话一个。委派代理从不持有对它的引用；
   它只能通过运行时为其构建的工具访问它。
2. 三个工具，可与现有七个工具一起在定义的 `tools:` 列表中声明：
   - `PeerSend(to?, text)` — 向一个正在运行的对等代理投递一条备注；省略 `to` 时投递给所有对等代理。
   - `PeerInbox()` — 清空排队的消息并列出正在运行的对等代理；从不阻塞。
   - `PeerWait(timeoutSeconds?)` — 阻塞直到有消息到达、超时到期、最后一个对等代理离开，或运行被中止。
3. **寻址依据是 peer id，而非委派 id。** 当某定义只有一个委派在运行时，其 peer id
   等于其代理名称。当同一定义的多个委派并发运行时（例如三位 "discussant" 圆桌参与
   者），每个都会通过在末尾追加数字后缀（"discussant-2"、"discussant-3"）获得唯一的
   peer id，从而使每个对等代理都可被单独寻址。暴露委派 id 会让委派代理拿到委派注册表
   的句柄，而那是父代理专属的。
4. **发送者在生成时绑定。** 每个对等工具都闭包持有该委派代理自身的代理名称（由运行时
   提供），因此 `from` 不是模型输入，委派代理既不能伪造发送者，也不能读取其他收件箱。
5. **可选启用且默认关闭。** 未声明任何对等工具的定义保持不变，因此每个既有定义——
   包括全部四个内置定义——都完全保持 ADR 0062 的隔离。没有任何内置定义声明对等工具。
6. **对等工具不出现在 `toolCatalog` 中。** 它们在生成时按委派代理逐一构建。父代理已经
   通过四个 `Task*` 工具拥有委派生命周期，不应再获得一条通往其委派代理的、更弱的
   第二条通道。
7. **对等工具不是主机工具调用。** 消息在进程内传递，因此它们绕过 `scopeDelegateTools`，
   不携带 `permissionScope`，从不抵达主机核心，也不消耗工具预算。没有什么需要门控：
   没有文件、没有进程、没有网络。
8. **对等消息流量从不进入父代理的模型上下文。** 父代理仍然只获知报告中所说的内容。
   委派代理在其提示词中被告知：任何对父代理重要的事也必须写进它的报告。
9. **仅能发消息不算委派代理。** 只声明对等工具的定义会在 `Task` 时被以工具错误拒绝：
   它能说话，但不能干活。
10. 每个维度都有界，因为邮箱是代理之间的共享可变状态，而每个代理都在努力填满自己的
    上下文：每条消息 2,000 字符、每个收件箱 32 条消息（最旧的先被丢弃，并向读取者报告
    该丢失）、每次运行 40 次发送，以及 `PeerWait` 上限 120 秒，对应 300 秒的委派代理
    空闲看门狗。
11. **读取即清空。** 消息一经读取即从邮箱中消失；委派代理自身的上下文是唯一的副本。
12. **成员关系跟随正在运行的委派代理。** 委派代理在启动时加入，在结算时离开。离开会
    唤醒所有等待者，因此停驻在 `PeerWait` 上等待某个刚刚退出的代理的委派代理会立即
    返回，而不是等满超时。
13. **peer id 对每个并发委派都是唯一的。** 当某定义声明了对等工具时，每个委派都会获得
    唯一的 peer id 和自己的邮箱收件箱。第一个委派保留裸名称（"discussant"）；同一定义
    的后续并发委派获得带后缀的 id（"discussant-2"、"discussant-3"）。这确保每个委派
    代理都能被单独寻址，也能单独寻址他人，对于结构化圆桌辩论等多实例模式而言这是
    必需的。

IPC、存储、主机协议或渲染器均无改动。`AgentEventEnvelope` 不受影响：对等消息就是发送
或读取它们的委派代理的工具调用，因此它们已经以 `parentToolCallId` 和 `agentName` 归属
出现在对话记录中，无需新的线上契约。

## 影响

- 两个具备写能力的委派代理可以在编辑文件之前先声明占用它们，从而让路径锁从唯一的
  协调原语回归为它本应是的那道兜底。
- 证伪了共享假设的委派代理可以在其对等代理仍能据此行动时说出来，而不是等到
  `TaskWait` 之后、它们的回合已然耗尽。
- 父代理的上下文开销不变。过去不可能做到的协调不会变成父代理的上下文；它留在委派
  代理之间。
- 对等消息在对话记录中以普通的委派代理工具调用出现，因此审阅扇出过程的用户无需新的
  UI 表面就能看到委派代理之间说了什么。
- 调用方必须遵守四条不变量：
  - **对等工具绝不能加入 `toolCatalog`。** 那会让父代理获得 `PeerSend`，从而获得一条
    绕过 `Task` 的简报与报告边界注入消息的途径。
  - **`from` 必须始终由运行时提供。** 一旦发送者名称变成工具参数，对话记录中的归属
    就变成模型的主张。
  - **已结算的委派代理必须离开邮箱。** 残留的参与方会让 `PeerSend` 对一条永远不会
    有人读取的消息报告成功，并让等待者阻塞在一个已经不存在的代理上。
  - **`PeerWait` 的上限必须保持在空闲看门狗之下。** 超过 300 秒静默的等待会让委派代理
    在等待中把自己杀掉，而失败会被读作委派代理卡死，而非问题无人回答。
- 委派代理现在可以把回合花在消息上。上限约束了最坏情况，提示词也明确协调不是闲聊，
  但选择启用的定义要接受其委派代理可能花掉几个回合做协调。
- 未涉及：跨会话消息传递、与父代理的消息传递、嵌套委派，以及对等历史持久化。这四项
  都留在范围之外。

## 考虑过的替代方案

- **让对等消息经由父代理中转：** 拒绝。委派代理运行时父代理被阻塞在 `TaskWait` 中，
  因此它无法及时中继；而且每一条备注都会落入委派机制本就要保护的上下文。这还让父代理
  的模型负责正确地转发它并不关心的消息。
- **让委派代理对其同级代理使用 `TaskList`/`TaskWait`：** 拒绝。那些是作用于委派注册表
  的生命周期工具。委派代理等待同级代理的*完成*而非消息，会重新引入死锁（两个委派代理
  互相等待），并把对并非由它启动的工作的控制权交给一个工作者。
- **以共享草稿文件作为通道：** 拒绝。它在今天就能用，而这恰恰是值得避免的失败模式：
  没有投递语义、没有边界、对话记录中没有归属，而且每个想监听的对等代理都要写轮询循环。
  它还把协调状态放进工作区或草稿树中，使其寿命超过会话。
- **为每个定义都始终启用对等工具：** 拒绝。它会一次性改变全部四个内置定义和每个既有
  用户定义的行为，而多数委派并不需要这种能力。审阅单个改动的 `code-reviewer` 没有可
  协调的对象，这个工具只会诱使它去四处张望。
- **采用中断式投递，把消息注入对等代理的下一次请求：** 拒绝。正在编辑中途的委派代理
  无法连贯地响应中断，而注入的消息会出现在委派代理并不想改变的上下文中。拉取式投递
  让委派代理掌控自己何时读取，代价是备注有时会被读得很晚——这正是提示词把每一次交流
  都定性为尽力而为的原因。
- **只广播、不支持定向消息：** 拒绝。常见情形是一个委派代理告诉某个特定的对等代理它
  占用了某个文件。把这条广播给八个委派代理，是用八个上下文去通知一个。
