## 上下文

ADR 0147 将 `A2A` 工具排除在父代理的目录之外，使父代理无法向自己的委派对象打开第二条更弱的通道。随后 ADR 0162 允许子代理寻址其他会话中的同级代理，但仍不能寻址父代理。

这种划分与用户的协作方式不符：他们希望侧边栏中的两个对话彼此协调，而不是两个嵌套的工作者。父代理是会话中唯一已经拥有用户上下文的代理。要求用户在每个聊天中生成一个 `discussant` 仅仅为了传递一条消息，是错误的切入方式。

broker 已经是进程全局的。每个会话运行时在首次 prompt 之后就已经存在于 sidecar 映射中。缺失的一环是父代理从未注册为 A2A 客户端。

剩下的风险就是最初那一个：如果父代理能够寻址自己的子代理，`Task` 的简报与回报边界就会崩塌。

## 决策

1. **每个 Agent 模式的会话运行时都会为其生命周期注册一个父 A2A 代理**（从首次 prompt 到 dispose）。卡片使用 `kind: "parent"`、名称 `parent`（由主机唯一化为 `parent-2`、…），以及携带会话标题的描述。Plan/Goal 运行时不会注册。
2. **`A2A` 是 Agent 模式父代理的核心工具**，从运行时构建时起就存在于目录中——而不是在 broker 注册之后。首次调用（或首次 prompt）会铸发 token。它不会出现在 Plan/Goal 中。
3. **类型不混用。** 代理卡片携带 `kind: "parent" | "subagent"`（默认为 `subagent`）。`a2a.agents.list` 与收件方解析只考虑调用方的类型。父代理不能发送给子代理；子代理不能发送给父代理。因此，同一会话内父代理到委派对象的反向通道不可能存在。
4. **入站消息会加入父代理的下一个回合。** 发往父代理的事件会在其 peer id 上排队。调用过 `A2A(wait)` 的父代理会像现在一样被唤醒。如果父代理处于空闲状态，下一次 `prompt()` 会在用户文本前面追加一个简短的 A2A 收件箱，让模型在无需单独自动启动回合的情况下看到另一个对话的消息。
5. **可触达性与运行时生命周期一致。** 一个对话在本进程中获得 Agent 运行时之后（即首次 agent prompt 之后）即可被发现，直到该运行时被 dispose 为止。没有存活运行时的侧边栏行不在注册表中。

保持不变：能力 token、对端事件路由、`recipientContextId` 投递、父代理仍使用 `Task*` 处理自己的委派对象、无远程 A2A、无嵌套委派。

## 后果

- 同一主机上的两个 Agent 对话可以彼此 `discover` / `send` / `wait` / `complete`。
- 省略 `to` 的父代理会寻址唯一的另一个存活父代理；当存在多个时则返回 `A2A_NO_PEERS`——与 ADR 0162 用于远程子代理的规则相同。
- 子代理的 A2A 不再列出父代理卡片，因此圆桌讨论无法通过 A2A 呼叫用户。
- 空闲对话在收到入站 A2A 时不会启动供应商回合；该消息会等待用户在该会话中的下一条消息。
- 未处理：自动唤醒空闲对话、寻址从未在本进程中运行过的会话，以及父代理到外部子代理的寻址。

## 已考虑的备选方案

- **让父代理保持无 A2A；由用户生成讨论者：** 已否决。那不是跨对话协作；而是用户并未要求的嵌套工作者协调。
- **允许父代理寻址每个存活代理：** 已否决。这会重新打开 ADR 0147 关闭的父代理→自有委派对象反向通道。
- **在空闲会话中自动启动回合：** 本次变更已否决。它会消耗一条用户并未发出的供应商请求，并且需要一个 sidecar 无法铸发的持久化宿主回合。一旦两个对话都在使用中，基于下一次 prompt 的收件箱就足以协作。
