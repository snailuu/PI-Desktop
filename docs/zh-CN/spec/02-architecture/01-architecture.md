# 01. 架构

> **翻译说明：** 本页是与 [英文源规格](/spec/02-architecture/01-architecture) 一一对应的机器辅助翻译。代码、协议字段和标识符保持原文；如翻译与英文源事实有歧义，以英文版本为准。

## 1. 概述

PI-Desktop 采用分层的桌面架构：

```text
┌──────────────────────────────────────────────────────────┐
│ 渲染器（React UI，英文优先 i18n）                        │
│ - 对话 / 会话 / 设置 / 插件 / 命令面板                   │
│ - 无 Node 集成                                           │
└───────────────────────────▲──────────────────────────────┘
 │ 预加载 IPC
┌───────────────────────────┴──────────────────────────────┐
│ Electron Main（轻量编排器）                              │
│ - 窗口生命周期                                           │
│ - IPC 路由                                               │
│ - 进程监管                                               │
└───────────────▲─────────────────────────────▲────────────┘
 │ 本地 RPC                 │ 进程桥接
┌───────────────┴──────────────┐ ┌──────────┴─────────────┐
│ Rust 主机核心                │ │ Node pi Agent Sidecar  │
│ - 工具 + 沙箱                │ │ - pi-ai                │
│ - 权限网关                   │ │ - pi-agent-core        │
│ - 插件宿主服务               │◄─►│ - 回合编排             │
│ - 持久化适配器               │ │ - 供应商流式输出       │
│ - 密钥适配器                 │ └────────────────────────┘
└──────────────────────────────┘
```

## 2. 设计原则

1. **UI 与特权运行时相互分离**
2. **Rust 掌管宿主/系统能力、持久模式与审批策略**
3. **pi 掌管模型/代理循环语义**
4. **渲染器不享有特权**
5. **所有跨边界契约都是强类型的**
6. **英语是产品源语言**
7. **Plan 是同一个 pi Agent 的一种状态，绝不是第二个规划器**

## 3. 子系统

### 3.1 应用外壳（Electron）
- 窗口/菜单
- 应用生命周期
- 固定源更新检查/下载/安装生命周期
- 进程启动顺序

Electron 主进程独占更新客户端以及固定的 GitHub Releases 目标。渲染器可以请求白名单内的操作并渲染强类型状态，但不能提供 feed URL，也不能直接访问更新器。应用更新不经过 Rust 主机核心或代理 sidecar（D120 / ADR 0022）。

### 3.2 UI（React）
- 会话用户体验
- 流式对话记录
- 权限卡片
- 设置
- 插件管理器 UI
- 命令面板

### 3.3 Rust 主机核心
- 工作区路径强制校验
- 内置工具执行
- 权限策略评估
- 持久会话模式解析（`agent | plan`）
- Plan 批准记录、请求，以及原子的 Plan → Agent 转换
- 插件安装/注册表/生命周期服务
- sqlite 适配器 / 安全存储粘合层
- 审计日志

### 3.4 Node pi 代理运行时
- 模型目录/供应商设置
- `Agent.prompt/abort`
- 对 pi 事件的归一化
- 向主机核心发出的工具调用请求
- 单 Agent 规划状态、由主机写入的 Plan 检查点提交，以及批准/拒绝执行边界

### 3.5 插件系统
- manifest 校验
- 贡献注册表（命令/工具/技能）
- 插件面板
- 权限授予

## 4. 请求路径（对话 + 工具）

```text
1. UI 提交提示词
2. Electron 主进程路由到代理 sidecar
3. pi 运行时启动回合并流式推送事件
4. UI 渲染文本增量
5. 工具调用时：
 5.1 pi 通过主机桥请求工具执行
  5.2 Rust 解析持久会话模式，并在权限模式之前评估权威的
      Plan/Goal/Agent 工具策略
  5.3 UI 在需要时进行确认，包括单独的 Plan/Goal 批准请求以及
      Bash 所选的 shell 身份
  5.4 Rust 解析该持久会话所属的项目，并在该工作区沙箱中执行工具
     （绝不使用当前激活的侧边栏标签页）
  5.5 结果返回 pi 运行时
6. 回合结束；会话持久化更新
```

当同一个 Agent 调用 `SubmitPlan` 时，主机核心会把完全相同的 Markdown 字节保存在一个新的不可变工件 `<workspaceRoot>/.pi/plan/*.md` 中，在 `plan_approvals` 中记录其相对路径/哈希/大小以及结构化的标题/问题，然后等待 `plans.resolve`。批准卡片会打开该工件。批准会把持久会话原子地切换为带有所选权限模式的 Agent，并排队一个全新的执行回合。拒绝、过期、主机/sidecar 崩溃以及持久化失败都不会授予任何执行能力。启动事务会在 RPC 服务启动前中断待处理的批准以及排队/运行中的执行字段，且不做重放；一个已被批准但被中断的执行会让会话停留在 Agent。

渲染器可以显示 Plan 状态和审批 UI，但它只是当前渲染器生命周期内主机/运行时实时事件的投影。它按会话在渲染器内存中保留最新的方案/执行快照；渲染器重新加载时只会通过 `plans.pending` 重新水合仍处于待处理状态的行，而不会重新水合已终结的批准或执行卡片。它无法通过发送冲突的请求字段来为某个工具授权，或替主机策略选择模式。

渲染器可以保留多个项目标签页，但这并不会产生多个主机工作区单例。一个项目提供可见的外壳上下文；与会话绑定的项目身份提供每个回合的特权工具根目录。

## 5. 为什么采用 Rust + pi 混合架构

| 方案 | 结论 |
|---|---|
| 全部由纯 TS 的 Electron 主进程处理 | 更简单，但系统边界更弱 |
| 用 Rust 完整重写代理循环 | 代价过高，且会丧失 pi 的既有优势 |
| **Rust 主机 + pi sidecar** | 已选定：强主机 + 成熟的代理引擎 |

## 6. 进程模型

传输方式：Rust sidecar + stdio JSON-RPC（NDJSON）。

MVP 目标进程：

1. Electron 主进程
2. Electron 渲染器
3. Rust 主机核心 sidecar
4. Node pi 代理 sidecar

开发模式可能会把某些服务放在一起运行，但契约保持不变。

## 7. 扩展点

- 工具供应商（内置 / 插件 / 后续的 MCP）
- 会话后端
- 模型目录来源
- 权限策略包
- 语言包
- 市场供应商（MVP 之后）

## 8. 打包影响

桌面安装包必须包含：

- Electron 应用
- 一个目标平台原生的 Rust 主机二进制文件
- 一个打包的 pi sidecar 入口 `Resources/agent-runtime/sidecar.js`，由 Electron 二进制文件以 `ELECTRON_RUN_AS_NODE=1` 运行
- 所有随产品发布的语言目录，以及仅为这些产品语言所需的 Chromium 语言包
- 仅在某个保留能力无法安全打包时，才包含目标平台原生的运行时模块

仅渲染器使用的库属于构建输入。Vite 必须把它们的可执行代码和懒加载资源输出到 `out/renderer` 下；electron-builder 不得再把它们原始的 production `node_modules` 目录树一并复制进 ASAR。Electron 主进程可以内联纯 JS 的工作区辅助代码，而原生模块或由运行时解析的模块保持为外部依赖。发布包会排除依赖的 source map、测试、示例、声明文件以及非目标平台的原生预构建产物，并且不会用网络下载来替换本地资源。
