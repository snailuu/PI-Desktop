## 1. 核心不可变规则

以下六条规则约束对 PI-Desktop 代码库与文档的每一次变更。未经明确的人工覆盖，代理不得放宽这些规则。

### R1 — 规格先行 / 规格同步

> **没有对应的规格更新，就没有行为变更。**

- 任何改变可观察行为的代码、配置或 UX 变更，都必须在该变更之前或同时更新相关的 `docs/spec/` 文档。
- 架构边界变更（进程模型、IPC 契约、存储归属、安全边界）还需要一份 ADR —— 参见 `docs/adr/README.md`。
- 保持行为与 API 契约不变的纯重构不需要更新规格，但仍必须提交（R2）。

### R2 — 每次变更均须提交

> **每一个完成的逻辑变更都必须进行 git 提交。**

- 不允许存在大量未提交的积压工作。每一个逻辑工作单元 —— 一个功能、一个修复、一次规格更新、一项杂务 —— 都应有独立的提交。
- 会话结束时仍有未提交的工作即违反本规则。
- 如果变更尚未完成，要么以 `WIP:` 前缀作为草稿提交，要么将其回滚。

### R3 — E2E 覆盖文档

> **每一个影响用户可见或协议可见行为的功能/修复都必须更新 e2e 测试文档。**

- “用户可见”：终端用户能看到或与之交互的任何内容（UI、CLI 输出、对话框、通知）。
- “协议可见”：IPC 消息、RPC 方法、插件 API 界面、事件负载。
- 在 `06-delivery/04-e2e-test-plan.md` 中记录该场景 —— 即使自动化测试尚不存在也应如此。
- 纯内部变更（日志格式、内部变量重命名）不需要更新 e2e 文档。

### R4 — 请求分支 + worktree + 合并门禁

> **每一个新请求都从 `main` 出发，在专用 worktree 中的专用分支上进行，并且只有当其 PR/MR 合并进 `main` 后才算完成。**

- 在编辑之前，保留任何已有的未提交工作，获取 `origin/main`，在其
  worktree 干净时快进本地 `main`，并从该最新提交创建新的请求分支和
  worktree。绝不能仅仅为了启动新请求而移动、贮藏或覆盖主检出中的
  现有工作。
- 每个请求使用一个短生命周期分支。命名方式为
  `<type>/<short-description>`，其中 `type` 在可行时匹配常规变更类型，
  例如 `feat/provider-import` 或 `docs/request-branch-workflow`。
- 每个请求使用一个专用 worktree。不要在主检出中实现新请求，也不要
  复用另一个请求的 worktree。
- 在安全的地方复用主检出的开发环境：已安装的工具链、包管理器存储、
  构建缓存以及被忽略的本地环境配置仍作为规范环境。需要时以引用或
  链接的方式将这些资源引入请求 worktree；不要将环境状态复制进受
  跟踪的文件。仅当隔离性或版本兼容性要求时才安装或生成 worktree
  本地状态。
- 禁止在 `main` 上直接开发提交和直接推送。
- 在完成开发及任何必要的本地验证之后，推送请求分支，打开以 `main`
  为目标的拉取/合并请求，并完成所有必需的远端检查与评审。
- 将已批准的 PR/MR 合并进 `main`，移除请求 worktree，并删除请求
  分支。如果认证、权限、必需的远端检查或必需的评审阻止了合并，
  请报告该阻塞项；此时请求不算完成。
- worktree 清理是强制且即时的。只要请求分支被集成进 `main` —— 包括
  请求未经过远端 PR/MR 而通过本地 `main` 合并交付的情况 —— 就立即
  移除该 worktree 并删除已合并的分支。已合并的请求不得在磁盘上留下
  worktree。只移除你自己的 worktree 和分支，并且只有在确认合并提交
  已存在于 `main` 之后才这样做。

### R5 — 开发前验证关联的 GitHub issue，然后回复并关闭

> **在报告的问题被证明存在之前，关联的 GitHub issue 不是一项任务。在结论明确之后，在该 issue 上回复并将其关闭。**

当用户提示中包含 GitHub issue URL 或本仓库明确的 issue 编号时，
本规则适用。

- 在为所声称的问题创建 worktree 或更改文件之前，先获取该 issue
  （标题、正文、标签、评论和状态）。
- 针对当前代码库独立验证该声明。对于 bug，复现它或引用具体的
  代码/规格证据。对于功能或改进，确认所请求的行为确实缺失或不完整，
  且在当前范围内。
- 在验证确认问题存在之前，不要开始实现。
- 如果问题不存在（已修复、无效或出于误解）：在有证据时注释说明验证
  证据，并在结论明确时关闭该 issue。如果验证无定论，注释说明尝试过的
  内容并保持该 issue 开放。
- 如果问题存在：遵循 R4，实现最小且连贯的变更，并在请求合并进本地
  `main` 之后，注释说明解决方案并关闭该 issue。
- 用原始 issue 标题和正文所用的语言撰写 GitHub 评论。代码、提交、规格
  以及其他仓库文档保持英文。
- 一个 issue 链接仅授权对**该** issue 进行评论和关闭。它不授权 git
  推送。远端发布仍须依照 R4 和 `AGENTS.md` 选择加入。
- 不要评论或关闭不相关的 issue。除非用户明确要求，否则不要重新打开
  已关闭的 issue。

### R6 — 合并原理合理的关联拉取请求，然后跟进

> **原理合理的关联 GitHub 拉取请求先被合并。完整性、风格、规格同步和打磨在合并之后进行，以免丢弃贡献者的工作。**

当用户提示中包含 GitHub 拉取请求 URL 或本仓库明确的拉取请求编号时，
本规则适用。

- 在创建替代实现或要求重写之前，先获取该拉取请求（标题、正文、文件、
  提交、评论、检查、草稿状态、base/head 以及关联的 issue）。
- 独立判断其**原理**是否合理。该变更必须解决一个真实的、在范围内的问题，
  且其方法必须与基线、安全边界和架构兼容（或是有充分理由、有规格支持的
  修订）。判断其方向，而不是判断该拉取请求是否已满足 R1–R5 的完整性。
- 当原理合理时，不要将拉取请求作为替代品重新实现、因细枝末节将其关闭或
  要求贡献者从头开始。
- 如果原理合理：
  1. 先合并**该**拉取请求，保留贡献者的提交。使用仓库允许且能保留
     贡献者作为落地工作作者的合并策略。
  2. 缺失的规格、测试、i18n、e2e 文档、风格、命名以及提交消息的细枝末节
     属于跟进工作，不是合并阻塞项。
  3. 会破坏 `main` 的落地阻塞项（该变更无法编译、变更所在区域的既有测试
     失败或有合并冲突）可以在作者的提交**之上**添加最小提交以便拉取请求
     落地。不要压缩掉作者。不要重写设计。
  4. 拉取请求进入 `main` 之后，从更新后的 `main` 出发，对任何跟进改进遵循 R4。
  5. 用该拉取请求的语言进行评论：致谢贡献，说明已合并的内容，并列出
     跟进事项（如有）。
- 如果原理不合理，或存在危害性阻塞项（机密、沙箱或权限绕过、恶意或明显
  破坏性的变更、对已冻结决策的越界逆转、不相关的顺手负载）：不要合并。
  用该拉取请求的语言附上证据进行评论。不要悄悄地把同样的想法重新实现，
  仿佛该拉取请求从未存在过。
- 不要合并作者尚未标记为就绪的草稿拉取请求，除非用户明确要求合并该草稿。
  评论说明原理评审，并等待其就绪。
- 当本规则适用时，一个拉取请求链接授权评审、评论并合并**该**拉取请求。
  它不授权强制推送贡献者的分支或发布不相关的分支。跟进仍须遵循 R4 的
  远端发布选择加入规则。
- 不要评论或合并不相关的拉取请求。已合并的拉取请求不再被重新打开；剩余的
  缺口成为普通的跟进事项。
- 当同时关联了 issue 和拉取请求时，R6 适用于拉取请求，而 R5 在合并结果
  之后仍适用于该 issue。

### GitHub issue 模板

`.github/ISSUE_TEMPLATE` 是唯一的公开录入路径（`blank_issues_enabled:
false`）。英文是源标签语言；中文保持在相同字段上。

- **Bug 报告**要求：描述、复现步骤、预期行为、实际行为、应用版本和操作系统。
  日志、额外环境和截图是可选的。从应用内打开时，设置 → 信息 会预填版本、
  操作系统和环境（D313）。
- **功能请求**要求：问题和拟议的变更。备选方案和额外上下文是可选的。

不要削弱这些必需字段。空白 issue 保持禁用。

## 2. 开发循环

每一次变更都遵循此顺序。如果实现过程中暴露出新的需求，可以迭代这些步骤。
如果提示中包含 GitHub issue，则在步骤 1 之前完成 R5 验证。如果提示中包含
GitHub 拉取请求，则在开始替代或跟进实现之前完成 R6 原理评审（并在合理时
先行合并）。

```
0. 如果关联了 GitHub issue：在任何实现之前验证该声明（R5）
0b. 如果关联了 GitHub 拉取请求：评审原理（R6）；合理时先行合并；只有进入 `main` 后才开始跟进
1. 同步 main + 创建请求分支和 worktree
2. 阅读基线 + 相关规格
3. 规划变更 + 列出受影响的规格与必要的验证
4. 实现
5. 如需，更新规格 / ADR / decisions-log
6. 当 R3 适用时更新或新增 e2e 场景
7. 针对变更风险运行所需的最小定向本地检查；在本地验证不必要时跳过，直接进入步骤 8。仅在用户明确请求时运行 E2E
8. 以常规消息提交
9. 如与里程碑相关，更新 BOARD
10. 推送分支 + 向 main 打开 PR/MR
11. 通过远端门禁 + 合并 + 移除 worktree 和分支
```

### 逐步说明

| 步骤 | 操作 | 产出 |
|---|---|---|
| **0. issue 验证** | 当关联了 GitHub issue 时，获取它并独立验证所报告的问题确实存在。当问题不存在时，在此停止（评论，且仅在结论明确时关闭）。 | 已验证的 issue，或一条评论加关闭/保持开放的决定。 |
| **0b. PR 评审** | 当关联了 GitHub 拉取请求时，获取它并独立判断原理是否合理。合理时先行合并；只有进入 `main` 后才开始跟进。不合理时停止（评论，不重写）。 | 已合并的贡献者 PR 加跟进计划，或一条评论且不合并。 |
| **1. 分支 + worktree** | 保留现有工作，从 `origin/main` 更新，并在专用 worktree 中创建专用请求分支。在安全的地方复用主检出的环境。 | 基于最新 `main` 的隔离任务文件，配有一致的开发环境。 |
| **2. 阅读** | 阅读 `00-baseline.md` 以及与变更领域相关的任何规格。 | 对约束的心智模型。 |
| **3. 规划** | 描述预期的变更。列出每一个需要更新的规格、ADR 和 e2e 场景，并评估本地验证是否必要。 | 变更计划 + 影响与验证列表。 |
| **4. 实现** | 编写代码、配置或资源。 | 更改后的文件。 |
| **5. 规格同步** | 按影响列表更新规格。如涉及架构则新增 ADR。如实现默认值改变则更新 `decisions-log.md`。 | 更新后的 docs/spec/\* 和/或 docs/adr/\*。 |
| **6. E2E 文档** | 当 R3 适用时，在 `04-e2e-test-plan.md` 中添加或更新场景条目，并链接到验收标准 ID（A–H）。否则确认无需更新场景。 | 更新后的 e2e 测试计划，或确认不适用。 |
| **7. 必要时验证** | 以变更风险和回归范围来决定本地验证是否必要。如果必要，运行最小相关的非 E2E 检查集，例如定向 lint、类型检查、单元/集成测试或构建。如果不必要，跳过本地验证，直接进入提交和交付。仅在用户明确要求 E2E 验证时运行 E2E。 | 定向检查结果，或评估为无需验证。 |
| **8. 提交** | 以常规消息进行 git 提交（见 §4）。 | 一个或多个提交。 |
| **9. BOARD** | 如果变更完成了一项里程碑交付物，更新 `docs/project/BOARD.md`。 | 更新后的看板。 |
| **10. 打开 PR/MR** | 推送请求分支并打开以 `main` 为目标的拉取/合并请求。 | 可评审的远端变更，并列出受影响的规格和验证情况。 |
| **11. 合并** | 通过必需的远端检查与评审，合并进 `main`，移除请求 worktree，并删除请求分支。 | 变更集成进 `main`；任务 worktree 和请求分支已移除。 |

### 本地验证与 E2E 执行策略

- 本地验证基于风险，而非交付的自动前提。仅文档的变更和低风险的机械式
  编辑通常不需要本地测试或检查，可直接进行提交、推送和创建 PR/MR。跳过
  它们无需单独的批准或豁免。
- 具有重大回归风险的变更，包括安全边界、协议契约、数据迁移、构建配置或
  广泛共享的行为，通常需要能够应对该风险的最小定向非 E2E 验证。默认情况
  下不是运行完整的本地测试套件。
- E2E 场景文档和 E2E 执行是两个独立的问题。对于用户可见或协议可见的行为，
  R3 仍要求更新场景。
- 代理不得主动运行 E2E 套件或命令，包括 `pnpm test:e2e*`、Playwright 套件、
  Electron 探测或实时代理 E2E 脚本。仅在用户明确要求 E2E 验证时才运行它们。
- 运行检查或测试的通用指令授权在步骤 7 下进行相关的非 E2E 验证；它不要求
  运行所有可用的本地检查，也不授权执行 E2E。
- 托管平台在推送或 PR 之后自动启动的必需 E2E 作业仍是合并门禁。观察并报告
  它们的结果，但不要手动分派或重跑，除非用户明确要求。

### 插件市场/更新诊断门禁

插件更新事故要求在更改代码之前采用证据优先的提示流程：

1. 捕获确切的插件 ID、已安装版本、显示版本、预期发布版本、目录 URL 和观察时间。
2. 获取实时目录并检查确切的条目，然后分别检查本地目录缓存和已安装注册表。
3. 对失败边界进行分类：发布者/目录数据、获取/缓存回退、宿主版本比较、IPC 传播，还是渲染器呈现。
4. 运行 `pnpm check:marketplace -- --url <catalog-url> --plugin <id>`。缺失
   `shasum`、`url`、正的 `sizeBytes` 或 `permissions` 是发布数据失败，而不是
   渲染器过期的证据。不完整的发布仍不可安装。
5. 在更改宿主或渲染器代码之前，用包含未排序版本和不完整元数据的 fixture 复现。

代理必须说明哪个边界失败，以及哪些证据排除了其他边界。客户端回退可以保留
安全发现，但不得用于掩盖无效的插件市场发布。

## 4. Git 提交规则

### 4.1 常规提交

格式：`type(scope): description`

| 类型 | 用于 |
|---|---|
| `feat` | 新功能 |
| `fix` | Bug 修复 |
| `docs` | 仅文档变更 |
| `test` | 新增或更新测试 |
| `chore` | 构建、依赖、工具、CI |
| `refactor` | 代码重构，无行为变更 |
| `perf` | 性能改进 |
| `build` | 构建系统或外部依赖变更 |
| `ci` | CI/CD 配置变更 |

**Scope** 是可选的，但鼓励使用 —— 例如 `feat(host-core):`、`fix(ui):`、`docs(spec):`。

### 4.2 语言

- 提交消息：**仅英文**（符合基线语言政策）。
- 正文：可选；用于非显而易见的上下文。

### 4.3 每次提交一个逻辑变更

- 优先使用小而有针对性的提交。
- 与代码变更紧密耦合的规格更新应放在同一个提交中。
- 纯文档变更（规格重写、ADR）可以是相邻的独立 `docs:` 提交。

### 4.4 绝不提交

- 机密、API 密钥、token、密码
- 仅本地数据（用户配置、会话数据、日志）
- `node_modules/`、构建工件、发布包
- 应按 CI 重新构建的生成文件

### 4.5 提交前检查清单

提交前，验证：

1. 变更是一个逻辑单元（或被明确拆分）。
2. diff 中没有机密或本地数据。
3. 规格按 §3 矩阵更新。
4. 如行为改变则更新 E2E 文档。
5. `git diff --stat` 审查 —— 没有意外内容。
6. 提交消息遵循常规格式。

## 5. 分支模型

仓库使用强制的请求分支和 worktree 工作流：

- **`main`** 始终可部署，且是受保护的集成目标。不要在其上直接开发、
  提交或推送。
- **请求分支和 worktree** 对每一个新请求都是强制的，包括文档、杂务和
  小修复。每个分支和 worktree 都从最新的 `main` 创建，然后在该分支
  合并进 `main` 后立即将二者移除。
- **分支名称**使用 `<type>/<short-description>`，描述为小写、kebab 式。
  允许的类型前缀镜像 §4.1。
- **不存在长期开发分支**。每个请求获得一个新分支；旧请求分支不得
  复用于不相关的工作。
- **主检出拥有默认开发环境。** 请求 worktree 在安全的地方复用其
  工具链、包管理器存储、缓存和被忽略的本地配置。请求在共享不安全
  或不兼容时，可以创建隔离的本地状态，但该状态保持被忽略，且不得
  泄漏到提交中。
- **PR/MR 交付**是强制的。推送分支，打开以 `main` 为目标的 PR/MR，
  通过必需的远端检查与评审，然后使用仓库允许的合并策略进行合并。

典型的请求启动（从主检出运行；选择主检出之外的路径）：

```bash
git status --short
git fetch origin main
git worktree add -b <type>/<short-description> <worktree-path> origin/main
```

如果 `main` 在干净的主 worktree 中已检出，则应在 `git worktree add` 之前
运行 `git switch main` 加上 `git pull --ff-only origin main`。如果主 worktree
不干净或位于另一个分支上，则保持其不变，直接从获取的 `origin/main` 创建
请求 worktree。绝不为了满足此顺序而丢弃、贮藏、移动或覆盖不相关的工作。

环境复用是针对具体资源的。包管理器存储和语言工具链通常自动共享。
被忽略的本地配置或兼容的依赖树在任务需要时可以从主检出引用或链接。
可能产生竞争的构建输出、可变运行时数据和不兼容的依赖树必须保持为
worktree 本地。

典型的 GitHub 交付（需要时使用托管平台的等价命令）：

```bash
git push -u origin <type>/<short-description>
gh pr create --base main --head <type>/<short-description>
gh pr checks --watch
gh pr merge --merge
git worktree remove <worktree-path>
git branch -d <type>/<short-description>
git push origin --delete <type>/<short-description>
```

当请求通过合并进本地 `main` 而非远端 PR/MR 被集成时的请求清理
（从主检出运行）：

```bash
git switch main
git merge <type>/<short-description>
git log --oneline -1
git worktree remove <worktree-path>
git branch -d <type>/<short-description>
git worktree prune
```

移除前 worktree 必须是干净的；先提交或丢弃请求自身的残留变更。使用
`git branch -d` 而不是 `-D`，这样未合并的分支会拒绝删除。如果
`git worktree remove` 报告该 worktree 为脏或被锁定，则解决该状态而不是
强制移除，并且绝不移除另一个请求的 worktree。

## 6. 完成的定义

当以下所有条件都成立时，一个变更才算**完成**：

1. 从最新的 `main` 创建了专用请求分支和 worktree。
2. 代码（或文档）实现了计划的变更。
3. 所有受影响的规格都已更新。
4. E2E 场景已记录（或按 §3 确认不需要）。
5. 必要的定向本地验证通过，或评估为不需要本地验证；自动触发的远端门禁
   通过，且代理仅在明确请求时才运行或分派 E2E。
6. 变更已用常规消息提交。
7. 如完成了里程碑交付物则更新 BOARD。
8. 提交中不存在机密或本地数据。
9. 分支已推送，其 PR/MR 已经过评审并合并进 `main`。
10. 请求 worktree 已移除，已合并的请求分支已删除。
11. 如果关联了 GitHub issue：开发前已验证该声明；该 issue 已用其语言收到
    评论；并在结论明确时已关闭该 issue。
12. 如果关联了 GitHub 拉取请求：已评审其原理；合理时先行合并；合并后落地
    跟进；贡献者的工作未被丢弃。

### 发布 / 版本标签门禁

当变更是**稳定应用版本发布**（版本号递增 + 打标签）时，完成的定义还要求在
打标签**之前**，每一个承载版本的界面都描述新版本：
`packages/shared/src/changelog.ts` 中随产品发布的语言环境的应用内更新日志条目
（英文及每一个随产品发布的产品语言环境，且亮点数量对齐），及其
`changelog.test.ts` 列表、每一个 workspace 的 `package.json`（包括
`docs/package.json`）、Cargo workspace 版本和 `host-core` 锁文件条目、
`APP_VERSION`，以及 `README.md` + `README.zh-CN.md` 中声明的发布行。
`node scripts/check-release-docs.mjs` 必须通过；`scripts/release.mjs` 会运行它，
否则拒绝打标签。参见
[06-release-runbook.md §4.1](/zh-CN/spec/06-delivery/06-release-runbook#41-mandatory-release-version-surface-gate-d164--d260)、
D164 和 D260。GitHub 发布说明不是替代品。

## 7. 禁止的做法

| 做法 | 原因 |
|---|---|
| 提交机密 | 安全违规 |
| 大量未提交的 diff | 违反 R2；丧失粒度 |
| 不更新规格就改变行为 | 违反 R1；规格变得不可靠 |
| 对用户可见变更跳过 e2e 文档 | 违反 R3；可追溯性缺口 |
| 未经用户明确请求就手动运行或分派 E2E | 违反选择加入的 E2E 执行策略 |
| 将完整的本地测试/检查套件视为推送前的自动要求 | 忽视基于风险的验证，并在没有需求证据的情况下延迟交付 |
| 直接在 `main` 上开发、提交或推送 | 违反 R4；绕过隔离和评审门禁 |
| 在主检出或另一个请求的 worktree 中开发新请求 | 违反 R4；混合任务文件和本地状态 |
| 将请求分支复用于不相关的工作 | 混淆请求范围并削弱可追溯性 |
| 在其 PR/MR 合并之前就将工作标记为完成 | 违反 R4；变更尚未集成进 `main` |
| 在磁盘上留下已合并的请求 worktree | 违反 R4；陈旧 worktree 累积并引发跨请求污染 |
| 未经 ADR + 版本号递增就修改基线冻结决策 | 基线已冻结；变更需要正式流程 |
| 提交 CI 应重新构建的生成工件 | 仓库膨胀、合并冲突 |
| 在单个提交中混合多个逻辑变更且没有清晰消息 | 丧失历史粒度 |
| 在未验证问题存在的情况下实现关联的 GitHub issue | 违反 R5；在无效或已修复的声明上浪费工作 |
| 关闭关联的 GitHub issue 时没有用该 issue 的语言进行评论 | 违反 R5；没有留下结果的公开记录 |
| 关闭、重写原理合理的关联拉取请求，或要求其重做 | 违反 R6；丢弃贡献者的工作 |
| 仅仅因为缺失规格、测试、风格或代理工作流完整性就阻塞合理的关联拉取请求的合并 | 违反 R6；完整性是合并后的跟进 |
| 合并原理不合理或引入危害性阻塞项的关联拉取请求 | 违反 R6；先合并原则不适用于不安全或方向错误的变更 |
| 为落地关联拉取请求而强制推送贡献者的分支 | 违反 R6；落地修复应置于作者的提交之上 |
| 在未为每一个随产品发布的语言环境更新 `packages/shared/src/changelog.ts` 的情况下给稳定应用发布打标签 | 违反 D164 / D345 / 发布运行手册；该语言环境和版本的应用内 What's new 为空 |
| 在 `README.md` / `README.zh-CN.md` 仍声明较旧发布行的情况下给稳定应用发布打标签，或用 `--skip-docs-check` 绕过 `scripts/check-release-docs.mjs` | 违反 D260 / 发布运行手册；已发布的文档宣传的版本与发布不再匹配 |

## 8. 本工作流的验收标准

本工作流规格本身满足以下条件时即被接受：

- [ ] R1/R2/R3/R4/R5/R6 表述清晰，并与相关规格交叉链接。
- [ ] 开发循环已记录，并被 `AGENTS.md` 引用。
- [ ] 规格更新矩阵覆盖基线中的所有变更类型。
- [ ] Git 提交规则与现有仓库提交风格一致（`docs:`、`chore:`）。
- [ ] 要求每一个请求都使用从当前 `main` 创建的专用分支和 worktree。
- [ ] 请求 worktree 在安全的地方复用主检出的环境，而不提交本地环境状态。
- [ ] PR/MR 创建、远端门禁、合并和分支清理都是强制的。
- [ ] 请求分支合并进 `main` 后（包括本地合并交付），立即要求移除 worktree 并删除分支。
- [ ] E2E 执行是选择加入的，且需要用户明确请求，而 E2E 场景文档在 R3 下仍为强制。
- [ ] 本地验证基于风险；不必要的检查可以跳过，而不阻塞提交、推送或 PR/MR 创建。
- [ ] 完成的定义完整且可执行。
- [ ] 禁止的做法列表覆盖已知风险领域。
- [ ] `AGENTS.md` 指向本文档、`04-e2e-test-plan.md` 和 `05-change-checklist.md`。
- [ ] 关联的 GitHub issue 在实现前得到验证，随后用该 issue 的语言评论，并在结论明确时关闭。
- [ ] 原理合理的关联 GitHub 拉取请求先被合并，然后跟进；贡献者的工作不被丢弃。
- [ ] 所有索引已更新（NAV、delivery README、spec README、docs README、BOARD）。
